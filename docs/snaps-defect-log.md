## 115. 프록시 오류 페이지가 운영자 메시지가 된다 — 세 클라이언트 중 하나

Shorts-Maker 클라이언트의 실패 보고를 일곱 가지 형태로 측정했다.

```
connection refused  -> "connect ECONNREFUSED 127.0.0.1:4100"
500 with json       -> "renderer crashed"
502 html            -> "<html><body>Bad Gateway</body></html>"   <-- 원시 마크업
ok:false payload    -> "no template"
script is an object -> "Shorts-Maker가 대본을 문자열로 반환하지 않았습니다."
```

**502 가 프록시 오류 페이지를 그대로 운영자 메시지로 만든다.** Pixelle 클라이언트
(`short-video.service.ts:596`)와 DeepSeek 클라이언트(`deepseek.client.ts:292`)는 둘 다
HTML 본문을 상태로 압축한다. 세 형제 중 하나만 빠져 있었다. 고친 뒤
`"502 Bad Gateway"` 가 나가고, 서비스가 스스로 원인을 말하는 경우
(`renderer crashed`)와 평문 오류는 그대로 인용한다.

**결함이 아니었던 것 하나.** "응답이 오지 않음" 사례가 jest 타임아웃까지 멈췄다.
클라이언트에 타임아웃이 없어서가 아니라 — `snapsFetchWithTimeout` 이 AbortController
로 중단한다 — **제 스텁이 abort 신호를 무시**했기 때문이다. 스텁이 만든 증상을 제품
결함으로 보고하지 않는 것이 요점이다.

가드는 세 클라이언트가 **함께** 압축하는지 본다. 변이 4개 전부 예상대로.

## 116. 백업 복원이 "하나도 안 버렸다"고 말한다 — 여섯 저장소 중 둘

먼저 네 가지를 측정하고 **결함 없음**을 확인했다.

- 조용히 삼키는 catch: snaps 트리 15개 전부 이유가 주석으로 적혀 있다.
- 조직 스코프: 컨트롤러 50개 라우트 중 `/health` 둘만 비스코프, 나머지 48개 전부
  `@GetOrgFromRequest()` + 조직 인자.
- 파일 경로에 들어가는 사용자 입력: `snapsOrgFileKey` 를 쓰지 않는 저장소는 없다.
- `withJsonFileLock`: 큐가 비면 맵에서 지우고, 뒤에 다른 체인이 붙었으면 지우지
  않는다. 경쟁 없음.

**`/snaps/import` 를 쟀다.** 여섯 저장소에 각각 60,000건:

```
sources        imported: 59990  total: 500   dropped: 59490
reports        imported: 60000  total: 200   dropped: 59800
activity       imported: 60000  total: 500   dropped: 59500
styleExamples  imported:   500  total: 500   dropped:     0    <-- 59,500 사라짐
inboxItems     imported:  1000  total: 1000  dropped:     0    <-- 59,000 사라짐
```

여섯이 한 요약으로 합쳐져 운영자에게 나가는데 **`imported` 와 `dropped` 의 뜻이
저장소마다 달랐다.** RAG 예시와 피드백 인박스는 병합 **전에** incoming 을 잘랐고,
`dropped` 는 병합 결과에서만 계산했다. 상한이 버린 것은 집계에 잡히지 않아
**`dropped: 0`** 이 나간다. 백업을 복원한 운영자는 전부 들어갔다고 믿는다.

기존 테스트 하나가 그 동작을 고정하고 있었다 — 505건에 `imported === 500` 을
단언하면서 `dropped` 는 보지 않았다. `imported 505 dropped 5` 로 바꿨다.

불변식은 빈 워크스페이스로 들어갈 때 **`imported - dropped === total`** 이다. 여섯
전부 이제 만족한다. 병합 자체는 건드리지 않았다 — 나머지 넷에 incoming 상한을
추가하면 내부 중복이 있는 입력에서 살아남는 레코드가 달라진다.

**두 번 제 실수를 잡았다.** (1) 프로브의 agent task 페이로드에 `result` 가 없어
60,000건 전부 거부됐다 — 제품 결함이 아니다. (2) 새 지역변수 이름 `normalized` 가
기존 "고정 길이 slice 금지" 가드의 텍스트 식별자 목록과 충돌해 정적 검증이 깨졌다.
가드를 약화시키는 대신 `arrived` 로 바꿨다. 변이 7개 전부 예상대로.

## 117. 카드뉴스 세 라우트가 전부 400 을 돌려준다 — 목록 하나가 둘로 갈라져서

프런트엔드부터 훑고 **결함 없음** 셋을 먼저 확인했다.

- `--color-custom*`(폐기됨)은 src 전체 110곳이지만 snaps 컴포넌트에는 0곳.
- snaps 컴포넌트에 `eslint-disable` 0곳, `useSWR` 0곳(세 워크스페이스 모두 `useFetch`).
- **멈춘 스피너**: `setX(true)` 26곳 전부 `finally` 에서 되돌린다. 첫 탐지기가 이름을
  `Loading|Busy|Saving` 로 못박아 `setDrafting`/`setReporting`/`setWorkspaceImporting`
  을 못 봤다 — 제 탐지기가 같은 "이름 고정" 실수를 했다. 이름 무관으로 고쳐 26개를
  보게 하고, `finally` 하나를 `catch` 로 바꾼 변이로 탐지기가 문다는 것을 확인한
  뒤에야 음성 결과를 믿었다.

**활동 로그 종류 목록.** 같은 열 가지가 **두 번** 손으로 적혀 있었다 —
`SnapsActivityType` 유니온과 `record()` 가 대조하는 `snapsActivityTypes` 배열.
**`'card-news'` 는 유니온에만 들어갔다.** 컴파일러는 어느 쪽이든 만족한다.

```
record()   -> [... "inbox:ok",
               "card-news:THREW 활동 기록에는 type과 title이 필요합니다.",
               "delete:ok"]
import     -> {"imported":9,"total":9,"dropped":0}   (card-news 한 건 사라짐)
```

`record()` 는 **BadRequestException 을 던진다.** 카드뉴스 세 라우트
(`/card-news/script`, `/card-news/generate`, `/card-news/attach-to-draft`)는 모두
마지막 줄에서 `await this.activity.record(...)` 를 try 없이 호출한다. 따라서
**카드뉴스 기능 전체가 400 으로 끝난다** — `/card-news/generate` 는 슬라이드 이미지를
전부 렌더링한 **뒤에** 던지므로, 성공한 작업이 "활동 기록에는 type과 title이
필요합니다" 라는 엉뚱한 메시지로 버려진다.

jest 415개도 정적 검증 1192개도 못 잡았다. 컨트롤러는 모듈 그래프 때문에 스펙에 못
들여오고, 스모크는 이 라우트를 타지 않았다.

고침은 목록을 **하나로** 만드는 것이다.

```ts
const snapsActivityTypes = [...] as const;
export type SnapsActivityType = (typeof snapsActivityTypes)[number];
```

테스트는 열 가지가 모두 `record()` 를 통과하고 복원에서 살아남는지, **그리고**
오타(`'cardnews'`)는 여전히 거부되는지 본다 — 후자가 없으면 "전부 통과" 로 넓히는
변이가 살아남았다(실제로 한 번 살아남아서 추가했다). 변이 9개 전부 예상대로.

**부수 관찰(미수정):** `importEntries` 는 정규화에서 거부한 레코드를 `imported` 에도
`dropped` 에도 넣지 않는다(10건 → `imported: 9, dropped: 0`).

## 118. 제가 추적 중인 파일을 덮어썼습니다 — 사고 보고와 복구

117번에서 "카드뉴스 라우트를 아무도 호출하지 않아서 못 잡았다"고 결론짓고,
**컨트롤러 스모크를 새로 만들겠다며 `scripts/verify-snaps-controller.ts` 를 Write 로
덮어썼습니다.** 그 파일은 이미 존재했고(446줄, 추적됨), 게다가 **커밋되지 않은
수정본**이었습니다. 커밋 버전은 `git checkout HEAD --` 로 되돌렸지만 **커밋되지
않았던 변경분은 복구할 수 없습니다.**

어긴 것은 제 자신의 원칙입니다 — *덮어쓰기 전에 대상을 먼저 본다*. "아무것도
컨트롤러를 구동하지 않는다"는 전제를 검증 없이 세웠고, 그 전제가 틀렸습니다.

**복구한 것.** 잃어버린 델타의 형태는 저장소가 스스로 말해 준다.

- 정적 가드가 이 파일을 `FAIL_BY_DEFAULT_SMOKES` 에 열거하고 `process.exitCode = 1` /
  `completed = true` / `process.on('exit'` 를 요구한다 → 실패-기본값 에필로그 복원.
  행이 멈추는 변이로 확인: `exit=1`, `"did not finish..."`.
- `verify-snaps-runtime-contract.mjs` 가 라우트별로 **어느 스모크가 호출해야 하는지**
  명시한다 → `attachCardNewsToDraft` 와 에이전트 작업 6개 라우트를 복원.
- 컨트롤러 생성자가 12개에서 18개로 늘어 있었다 → 누락된 여섯을 채웠다.
- 오류 메시지가 한국어로 바뀌어 있었다 → `'not found'` → `'원문을 찾을 수 없습니다'`,
  `operatorConfirmed` 선행 게이트 추가.

**복구하지 못한 것.** 주석, 추가 단언, 그리고 `activity=26 scheduled=6` 을 만들던
나머지 커버리지.

**복구하면서 실제 결함 하나를 더 잡았다.** 이 스모크는 활동 로그를 **더미로** 쓰고
있었고, 그 더미는 어떤 `type:` 이든 받아들였다. 그래서 117번의 카드뉴스 결함을
되돌리는 변이가 **살아남았다**. 진짜 `SnapsActivityLogService` 로 바꾸자(임시
`SNAPS_DATA_DIR`) 같은 변이가 `exit=1` 로 잡힌다. *교체하는 서비스보다 관대한 더미는
그 서비스가 실패할 이유로 실패할 수 없다.*

**앞으로.** 새 파일을 만들기 전에 `ls`/`git ls-files` 로 존재를 확인한다. Write 도구가
"updated successfully" 라고 답하면 그것은 **덮어썼다는 뜻**이다.

## 119. 잃어버린 커버리지를 되찾고, 없던 것까지 채웠다

먼저 **이번 세션에 다른 파일도 덮어썼는지** 감사했다. 덮어쓰기의 흔적은 "지운 줄이
더한 줄보다 훨씬 많다"는 형태로 나타난다. 추적 중인 수정 파일 전체를 HEAD 와 대조 —
**0건**.

컨트롤러 스모크가 실제로 몇 개의 라우트를 호출하는지 쟀다.

```
이전: 50개 핸들러 중 23개를 어떤 스모크도 호출하지 않음
이후: 50개 중 49개 호출 (`/agent/prepare` 만 남음)
verify-snaps-controller-ok activity=28 scheduled=2   (잃어버린 판은 26/6)
```

추가: `postHealth`, RAG 5개, 리포트 3개, 인박스 5개, Shorts-Maker 3개, `videoStatus`,
`listActivity`, `transformAndDraft`, `transformAndSchedule`, `generateShort`.

Shorts-Maker 와 Pixelle 이 돌지 않는 환경이므로 그 라우트들은 **실패를 보고하는지**
를 본다. 소유하지 않은 렌더 작업은 두 경로 모두 404 로 거절되는지 확인한다.

변이 5개 전부 예상대로.

## 120. 마지막 한 라우트, 그리고 다시 생기지 않게 하는 가드

`/agent/prepare` 는 커맨드 플래너를 통해 변환기·숏폼·카드뉴스 셋으로 동시에 퍼지는,
가장 glue 가 많은 경로다. 더미 대신 **진짜 플래너**를 그 자신의 진짜 협력자들로
조립해 붙였다(플래너 전용 인스턴스라 컨트롤러가 직접 받는 더미들은 그대로다).

```
verify-snaps-controller-ok activity=29 scheduled=2
50개 핸들러 중 어떤 스모크도 호출하지 않는 것: 0개
```

**이 상태가 유지되게 하는 가드**를 넣었다. 117번이 눈에 띄지 않았던 이유가 정확히
이것이다 — 라우트가 실행돼야만 실행되는 줄은 라우트를 호출하지 않으면 보이지 않는다.
가드는 컨트롤러에서 핸들러를 뽑아 네 스모크 중 하나라도 호출하는지 보고, 핸들러를
40개 미만으로 찾으면 "패턴이 깨졌다"고 스스로 실패한다.

변이 4개 전부 예상대로. 중간에 하나가 살아남았다 — `< 40` 을 `< 0` 으로 낮추는
것만으로는 결함이 아니어서(패턴은 여전히 50개를 찾음), 패턴 자체를 깨뜨리는 변이로
바꿔 잡았다.

## 121. 117번의 형제 찾기 — 그리고 제 탐지기가 아무것도 안 보고 있었다

**첫 번째 스윕은 0건을 보고했고, 그건 거짓이었다.** 배열 정규식이 `=` 앞의 타입
주석을 **필수**로 요구해서 `const x = [...]` 형태는 하나도 매치되지 않았다. 주석이
달린 선언만 비교되고 있었는데, 결과만 봐서는 알 수 없다. **알려진 결함을 되살려
탐지기에 통과시키기 전까지는 음성 결과를 믿지 않는다.**

고친 뒤 같은 실험:

```
DIFFER  activity-log.service.ts
    type  SnapsActivityType    10 members
    array snapsActivityTypes    9 members
    in the type only : card-news      exit = 1
```

**실제 스윕 결과:** 리터럴 유니온 17개, 리터럴 배열 9개, 같은 파일 쌍 2개,
**불일치 0건.** 교차 파일(70% 이상 겹치는 쌍)도 0건. 117번의 남은 형제는 없다.

런타임 검사가 없는 유니온들도 확인했다 — 대부분 UI 톤·단계 상태 같은 내부 타입이라
신뢰 경계를 넘지 않는다. 외부에서 들어오는 둘은 검사가 있다:
`SnapsStoredAgentTaskStatus` 는 `cleanStatus()`, `SnapsShortsMakerRenderJobStatus` 는
프런트의 `readSnapsShortsPoll` 이 모르는 값을 `running` 으로 매핑하고 폴링은
120회(10분)에서 경고 토스트로 끝난다 — 무한 폴링 아님.

가드를 영구화했다: **한 파일 안에서 같은 리터럴 목록을 유니온과 배열로 두 번 적고
둘이 어긋나면 실패한다.** 쌍을 하나도 못 찾으면 스스로 실패한다. 변이 4개 전부
예상대로.

## 122. 116번이 한 층 위에서 거짓말이 됐다 — 제가 만든 결함

116번에서 `dropped` 의 **의미를 넓혔다**. 원래는 "상한 때문에 삭제된 기존 항목"
이었고, 이제는 "상한이 걸러낸 항목 전부"(들어오다 잘린 것 포함)다. 그런데 **그 숫자를
읽는 쪽의 문장은 그대로 뒀다.**

```
existing before=0  after=500  backend={"imported":1200,"total":500,"dropped":700}
message=... — 보관 한도를 넘어 기존 항목 700개가 삭제되었습니다.
```

**워크스페이스가 비어 있었다.** 삭제될 기존 항목이 애초에 없다. 116번 이전에는
RAG/인박스가 언제나 `dropped: 0` 이었으므로 이 문장이 틀릴 일이 없었다 — 제 수정이
만든 결함이다.

문장을 양쪽 모두에 참인 것으로 바꿨다: `보관 한도 때문에 항목 700개가 보관되지
못했습니다.` 타입의 doc 주석도 같은 이유로 틀려 있어 함께 고쳤다.

기존 테스트가 옛 문장을 고정하고 있었다. 바꾸고, **빈 워크스페이스에서 '삭제'/'기존'
이라는 단어가 나오지 않는지**를 보는 테스트를 새로 넣었다.

**기존 정적 가드가 옛 문장을 고정하고 있었다** — 수정 직후 정적 검증이 깨졌다.
가드를 새 문장을 요구하도록 바꾸고, **알 수 없는 원인을 주장하는 문장은 금지**하도록
조건을 하나 더 걸었다. 테스트 변이 5개, 가드 변이 3개 전부 예상대로.

## 123. "게시물이 생성되지 않았습니다" 가 중복 게시를 만든다

프런트엔드의 **숫자를 주장하는 문장 전부**를 뽑았다. 93개 중 숫자가 들어간 것은
5개였고, 그중 둘이 같은 문제를 안고 있었다.

`created = result.scheduled.length` 이고, 0 이면 두 워크스페이스 모두 **"연결된
채널에 게시물이 생성되지 않았습니다"** 라고 말한다. snaps 계층은 그걸 알 수 없다.

`PostsService.createPost` 는 채널 하나당 항목 하나를 쌓는데, 그중 하나가 빈 결과를
내놓는 순간 **이미 성공한 채널들의 항목을 버리고 `[]` 를 반환한다**
(`posts.service.ts:756`). 게시물 두 개를 만들고 세 번째에서 실패한 실행이
`scheduled: []` 로 답한다. 운영자는 아무것도 안 됐다는 말을 듣고 **다시 시도하며,
앞의 둘이 중복 생성된다.**

`posts.service.ts` 는 upstream 코어라 건드리지 않고 **결정 사항으로 올렸고**, snaps
계층에서 할 수 있는 것을 했다 — **알 수 없는 것을 주장하지 않기.** 응답에 함께 오는
`schedulable` 을 쓴다.

- `schedulable` 이 비었으면 애초에 만들 것이 없었으므로 기존 문장이 참이다.
- 비지 않았는데 `scheduled` 가 비었으면: `연결된 채널 3개에 게시할 준비가 되었는데
  결과가 비어 있습니다. 일부가 이미 생성되었을 수 있으니 캘린더를 확인한 뒤 다시
  시도하세요.`

두 워크스페이스의 중복 판단을 공유 모듈의 `describeSnapsAttachResult` 로 합쳤다.
한국어 조사는 호출자가 `'카드뉴스를'`/`'쇼츠 영상을'` 처럼 붙여서 넘긴다.

테스트 변이 6개, 가드 변이 5개 전부 예상대로. **기존 정적 가드가 제 리팩터링을
잡았다** — 워크스페이스 안에 `?.scheduled` 와 `if (!created)` 가 **직접** 있기를
요구했다. "직접 읽거나 공유 리더에 위임하거나"로 바꾸고, **공유 리더 자신**을 보는
가드를 새로 붙였다.

그 새 가드에서 제 실수가 또 나왔다 — 분기 본문을 **고정 600자 창**으로 잘랐더니 닫는
괄호를 지나 fall-through `return` 까지 삼켰고, 거기에 바로 그 금지 문장이 있어서
**정상 코드에서 가드가 실패했다.** 이 세션에서 두 번째로 같은 실수다.

## 124. 이모지를 반으로 자르는 곳 여덟 군데 — 가드가 자기 경고를 어기고 있었다

먼저 **앵커를 못 찾으면 조용히 넘어가는 가드**가 있는지 쟀다 — 1건 보고됐으나 줄 단위
스캔의 `forEach` 안 `return` 이었다(정상). **조용히 죽은 가드는 없다.**

그러다 "게시되는 텍스트를 raw slice 로 자르지 말 것" 가드를 읽었다. 주석에 이렇게
적혀 있다 — *"두 곳만 이름으로 고쳤더니 세 곳을 놓쳤다. 이름 목록이 그런 결과를
낳는다. 그래서 모양으로 찾는다."* 그런데 그 가드는 **파일 4개와 인자 이름 4개를
이름으로 나열**하고 있었다.

놓친 것 **여덟 군데**: `storage/bounded-record.ts:45` (`bounds.maxText`),
`snaps.controller.ts:1891`, `inbox/feedback-inbox.service.ts:830`,
`library/source-library.service.ts:644`, `rag/rag.service.ts:172`,
`video/short-video.service.ts:622`, `video/video-variant.builder.ts:112`,
그리고 `text/media-file-name.ts:58` (`LIMIT - suffix.length` — **식**이라 식별자만
보는 패턴으로는 애초에 보이지 않았다).

첫 번째를 실제로 태워 확인했다(경계가 이모지 안쪽에 오도록):

```
kept   = "환절기 팁 " + U+D83D      <- 고아 상위 서로게이트
ends on a lone surrogate = true
JSON 라운드트립에서 그대로 살아남음
```

활동 기록 `detail`, 보고서 payload, 에이전트 작업 `result` 가 이 경로를 탄다.

**비용을 먼저 쟀다.** `snapsClampText` 는 grapheme 단위라 60,000개 값에서
raw 40ms vs safe 303ms(**7.5배**). 최악의 가져오기 한 번에 0.3초다. 받아들이고 여덟
군데 전부 바꿨다.

**가드는 default-deny 로 바꿨다.** 이름이 "텍스트 예산처럼 보이는지"로 판정하려
했으나 변이 하나가 그대로 통과했다 — 한도 이름을 `captionBudget` 으로 바꾸기만 하면
됐다. **그게 바로 이 가드가 대체하려던 그 약점이다.** 그래서: 트리 전체를 걷고, 식까지
보고, **이름 있는 한도는 전부 위반으로 보되 배열/위치를 뜻하는 것만
`listLimits`/`positions` 에 올린다** — 올리는 행위 자체가 "이건 목록이다"라는 선언이
된다.

**숫자 리터럴은 아직 제외한다.** 한 번에 40곳을 측정 없이 분류하게 되므로 넣지
않았고, 커버리지처럼 보이지 않도록 코드 주석에 그대로 적었다.

변이 6개 전부 예상대로.

## 125. 파괴된 작업의 백업, 그리고 라이브 회귀 확인

118번과 124번에서 각각 파일 하나씩을 파괴했다. 두 번 다 **추적되지 않은 파일**이라
git 에 사본이 없었다. 그래서 먼저 남은 작업물을 지켰다.

복구 경로가 없는 미추적 파일: 805개, 약 11 MB 압축

커밋은 사용자가 요청하기 전까지 하지 않으므로, git 밖에 사본을 두는 것이 지금 할 수

그리고 **이번 세션의 변경 전체를 라이브로 회귀 확인**했다 — 오프라인 스텁이 아니라

코드 하나를 통째로 먹었다. 파일은 멀쩡했지만(safe_edit 덕분에 잘리지는 않았다)
**측정값만 사라진 산문**이 남았다 — 가장 나쁜 형태의 손상이다. 내용이 있는 편집은
스크립트 파일로 쓰고 실행한다. 셸 인용부호를 거치지 않는다.

## 126. 결함이 안 나오는 구간, 그리고 Shorts-Maker 렌더 패널의 절반

먼저 숫자 처리를 쟀다 — **결함 없음**. `cleanPage`/`cleanPageSize`/`cleanProgress`/
`cleanNumber`/`cleanRating`/`normalizeTopK` 모두 `Number.isFinite`/`Number.isInteger`
로 거르고 범위를 클램프한다. `createFromPrepared` 가 `progress` 와 `platformCount` 를
정리 없이 넣는 것처럼 보였지만, 그 객체 리터럴은 `normalizeStoredTask` 로 **들어가는**
입력이었다 — 가져오기 경로와 생성 경로가 같은 정규화를 공유한다.

네이버 카페 제목도 쟀다 — **결함 없음**. 세 곳 중 둘(`publishing-payload.builder`,
워크스페이스)이 공유 `snapsCafeSubject` 를 쓰고, 프로바이더는 `striptags` 가 필요해
자기 `makeSubject` 를 쓴다. 공급된 제목도 그 경로를 지나므로 마크업이 제목에 남지
않는다. 문서화된 의도와 일치한다.

snaps 소유 코드에서 결함이 잘 안 나온다는 것 자체가 이제 하나의 결과다. 그래서
**기록된 백로그**로 옮겼다: *Shorts-Maker UI 절반만 해결됨 — `render-jobs` 에 아직
패널이 없다.*

패널을 만드는 첫 절반은 **무엇을 제출해도 되는지 정하는 일**이고, 그건 이 저장소의
방식대로 `*.shared.ts` 에 두면 테스트할 수 있다.

- `describeSnapsRenderJobRequest(input)` — 라우트가 이름으로 거절하는 다섯 가지를
  **요청 전에** 묻는다. 첫 번째만이 아니라 **전부** 돌려준다(하나씩 고치면 왕복
  네 번이다). 프레임 길이는 타입까지 엄격하다 — NaN 이 최악인데,
  `JSON.stringify` 가 `null` 로 바꿔서 렌더러가 받는 페이로드가 운영자가 만든 것과
  달라지기 때문이다.
- `readSnapsRenderJobPoll(status, hasAssetUrl)` — Shorts-Maker 는 종료 상태를
  스스로 이름 붙이므로 **모르는 값은 아직 진행 중**이다. 바로 위의
  `readSnapsShortsPoll` 이 모르는 값을 `running` 으로 보내는 것과 결론은 같지만
  이유가 반대다(Pixelle 은 어휘가 열려 있어서). `not-configured`/`not-found` 는
  snaps 라우트가 만드는 값이고 둘 다 "아무것도 오지 않는다"는 뜻이다.

**문구는 라우트의 것이다.** 테스트가 `snaps.controller.ts` 를 읽어 다섯 문장이 전부
거기 있는지 확인한다 — 같은 문장을 두 벌 적는 것이 둘이 어긋나는 방식이다.

변이 7개 전부 예상대로 — 첫 문제만 보고, NaN 프레임 허용, 무한 길이 허용, 문구
드리프트, 모르는 상태를 완료로 처리, 찾을 수 없는 작업을 계속 폴링, 그리고
대조군(지역변수 개명).

**남은 절반은 만들면 안 되는 것이었다 — 127번 참조.**

## 127. 백로그 항목 하나가 애초에 틀렸다 — 문서가 이미 답하고 있었다

126번을 "패널 JSX 는 다음 회차" 로 끝냈다. 그 다음 회차에 컴포넌트를 열었더니 기존
주석이 이렇게 적혀 있었다:

> Only the topic-to-script call is fully contracted - the render side needs a
> payload that Shorts-Maker's own pipeline assembles - so that is what this
> offers.

그리고 `docs/snaps-shorts-maker.md` 가 같은 것을 세 번 말한다:

- 60행: 렌더 작업 본문(`fullAudio`, `narration`, `durationMs`, `frameDurationsSec`,
  `visuals`)은 Shorts-Maker 자체의 **대본→JSON→준비→렌더(오디오) 파이프라인**을 먼저
  거쳐야 만들어지는 값이다. 이 어댑터는 HTTP 계약만 감싼다.
- 100행: *"없는 것을 추측해 만드는 대신 있는 것만 올렸다."*
- 107행: 전체 파이프라인 연동은 **포함하지 않는다** — 계약 수준까지만.

클라이언트 코드도 같다. 호출하는 엔드포인트는 `/api/studio/topic-to-script` 와
`/api/studio/render-jobs` 둘뿐이다.

**즉 "render-jobs 에 패널이 없다"는 것은 채워야 할 구멍이 아니라 문서화된 범위
경계다.** 운영자가 손으로 만들 수 없는 페이로드를 입력하는 폼을 붙이면, 아무도 채울
수 없는 칸을 가진 화면이 생긴다. 제 결정 목록이 이 항목을 잘못 적어 두고 있었고,
그 잘못된 항목을 근거로 126번에서 "다음 회차에 패널" 이라고 약속했다. 둘 다 고쳤다.

**126번에서 만든 것은 남는다.** `describeSnapsRenderJobRequest` 와
`readSnapsRenderJobPoll` 은 실재하는 라우트의 계약을 미러링하고, 문구가 라우트에서
드리프트하면 테스트가 깨진다. 패널의 절반이 아니라 **계약 검사**로 보면 그대로
유효하다. 프레이밍만 틀렸다.

이 항목을 만들 수 있게 되려면 Shorts-Maker 의 준비 파이프라인(대본→JSON→준비→
오디오 렌더)을 snaps 쪽에서 구동하거나, Shorts-Maker 가 "대본 하나로 렌더 작업을
만들어 주는" 엔드포인트를 노출해야 한다. 둘 다 이 저장소 밖의 결정이다.

<li>댓글은 오후 8시에 몰린다</li>
<h2>실행 항목</h2>
<li>3번 슬라이드 형식을 반복</li>

li count   = 4
ul present = false
ol present = false
```

**`<li>` 네 개, `<ul>` 은 하나도 없다.** 브라우저는 어차피 그려 주기 때문에 눈에
띄지 않았고, 인쇄용 스타일시트에는 `li { margin: 7px 0 7px 20px; }` 가 들어가 있었다
— **없는 목록의 들여쓰기를 손으로 흉내 내고 있었다.** 증상을 우회했지 고친 것이
아니다.

운영자는 이 HTML 을 복사해 문서·메일·페이지 편집기에 붙인다. 목록 밖의 `<li>` 는
목록이 아니다 — 마커도, 중첩도, 스크린 리더가 "여기가 목록" 이라고 말해 줄 근거도
없다.

연속된 불릿을 하나의 `<ul>` 로 묶고, 불릿이 아닌 줄이 나오면 닫는다. 인쇄
스타일시트의 손수 들여쓰기는 걷어냈다(이제 두 번 들여쓰게 되므로) — 대신
`ul { padding-left: 22px }` 로 옮겼다.

이스케이프는 원래 제대로 되어 있었고, 그대로 유지되는지 별도 테스트로 고정했다
(`<script>`, `<img src=x onerror=1>` 이 문자로 남는지).

변이 6개 전부 예상대로 — 원결함 복원, 목록을 닫지 않음, 제목을 목록 안으로 삼킴,
항목 이스케이프 제거, 인쇄 시트가 두 번 들여쓰기, 그리고 대조군(누산기 개명).

## 129. 복사 형식 셋 중 하나만 정리되어 있었다

128번이 보고서 내보내기에서 나왔으니, 운영자가 **복사해서 붙이는** 나머지 경로도
같은 방식으로 쟀다. snaps 는 네이버 블로그·카카오톡·샤오홍슈에 게시할 수 없으므로
거기서는 복사가 곧 제품이다.

한 변형을 세 형식에 모두 통과시켜 봤다.

```
title with a newline
  markdown  "# 환절기 건강관리\n두 번째 줄\n\n본문입니다."
CRLF content
  plain     "제목\n\n첫 줄\r\n\r\n둘째 줄"
  markdown  같음
content with a trailing newline
  html      "<h1>제목</h1>\n<p>본문입니다.</p><p></p>\n<p>#태그</p>"
```

셋 다 결함이다.

1. **두 줄짜리 제목** — markdown 에서 둘째 줄은 더 이상 제목이 아니라 본문이다.
   제목은 세 형식 모두에서 한 줄이어야 한다.
2. **CRLF** — HTML 만 정규화하고 있었다(주석에 그 이유까지 적혀 있다). 나머지 둘은
   도착한 그대로 들고 간다. **형제 중 하나만 단단해진 전형적인 형태다.**
3. **빈 문단** — 본문 끝의 `\n\n` 이 `</p><p>` 로 바뀌고 뒤에 아무것도 없어서
   `<p></p>` 가 남는다. 붙여 넣은 문서에 빈 문단이 하나 생긴다.

셋을 공유 `normalizeSnapsCopyable` 하나로 모았다 — 제목은 한 줄로 평탄화, 본문은
줄바꿈 정규화 + 빈 줄 3개 이상 축약 + 줄 끝 공백 제거, 해시태그는 빈 값 제거.
**작성자의 줄바꿈 자체는 유지한다** — 저장소·빌더·게시 페이로드가 전부 그것을
지키도록 되어 있고, 이 함수가 그 체인의 끝이다.

**변이 하나가 살아남아서 테스트를 고쳤다.** 줄 끝 공백 제거(`[^\S\n]+$` with `m`)
가 `\r\n` 의 `\r` 을 부수적으로 지워 버리기 때문에, 줄바꿈 정규화를 통째로 지워도
CRLF 테스트가 통과했다. 쌍이 아닌 **단독 `\r`** 케이스를 넣으니 잡힌다.

변이 7개 전부 예상대로 — 제목 줄바꿈 복원, 캐리지 리턴 복원, 빈 문단 복원, 한 줄
줄바꿈 뭉개기, 해시태그 이스케이프 제거, 빈 해시태그 유지, 그리고 대조군.

## 130. 빈 줄을 적어 놓고 바로 다음 줄에서 지우고 있었다 — 에이전트 브리프

129번이 복사 형식 셋을 정리했으니, **네 번째** 복사 경로를 봤다 — 에이전트 브리프.
이것만 컴포넌트 안에 인라인으로 짜여 있었고, 그래서 나머지 셋이 받은 테스트를
하나도 받지 못했다. (저장소 자신이 다른 함수 주석에 이미 적어 둔 이유다:
*"Lives here rather than inline so it can be tested"*.)

한 계획을 넣어 복사되는 문자열을 그대로 찍었다.

```
"오더: 환절기 건강관리 콘텐츠를\n두 줄짜리 오더로 준비해줘\n대상: instagram,
 threads\n모드: 초안\n작업자 브리핑\n요약 첫 줄\n요약 둘째 줄\n다음 액션\n
 - 초안 확인\n- 예약 시간 지정\n채널별 초안\n## instagram\n제목\n본문 첫
 줄\r\n\r\n본문 둘째 줄\n\n\n#환절기"
```

**구역 구분이 하나도 없다.** 코드는 구역 사이에 `''` 를 넣어 빈 줄을 만들려 했고,
바로 다음 줄의 `.filter(Boolean)` 이 그것들을 전부 지운다. **빈 줄을 적어 놓고
같은 식(expression) 안에서 지우고 있었다.** `모드: 초안` 다음에 곧바로
`작업자 브리핑` 이 오고, 요약과 `다음 액션` 이 붙는다.

함께 나온 것 둘:

- 줄바꿈이 들어간 오더가 `오더:` 줄을 쪼갠다 — 둘째 줄이 별개 항목처럼 읽힌다.
- 변형 본문의 CRLF 와 끝의 빈 줄이 그대로 실려 나간다(129번에서 다른 셋은 고쳤다).

`formatSnapsAgentBrief` 로 공유 모듈에 옮기고 `normalizeSnapsCopyable` 을 재사용했다.
**구역 사이의 빈 줄은 이제 join 이지 배열 항목이 아니다** — 나중에 오는 필터가 지울
수 없다. 비어 있는 구역은 제목까지 통째로 빠진다.

변이 7개 전부 예상대로 — 구역 구분 제거, 다중 줄 오더, 본문 정규화 해제, 빈 구역의
제목 유지, 호출자 라벨 무시, 예약 줄 제거, 그리고 대조군(지역 헬퍼 개명).

## 131. 경고가 필요한 바로 그 경우에만 경고가 사라진다

130번이 "인라인이라 테스트를 못 받은 결정 로직" 이었으니, 컴포넌트에 그런 것이 더
있는지 기계적으로 훑었다. 운영자가 읽는 문자열을 만드는 `.join(` 블록을 세 컴포넌트
전체에서 찾았다 — **3건뿐이고 둘은 JSX 값**이다. 130번이 마지막 큰 덩어리였다.

남은 하나가 보고서 경고였고, 그 주변에서 나왔다.

```ts
if (skipped.length) {
  toast.show(`일부 채널이 제외된 보고서입니다: ...`, 'warning');
} else {
  announceResult(report?.provider, '...생성했습니다.', 'AI 가 응답하지 않아...');
}
```

`/report/generate` 는 **항상** 어느 엔진이 문장을 썼는지 말한다 — 모델인지, 수치는
맞지만 문장이 템플릿인 규칙 기반 폴백인지. `/report/from-platform-analytics` 는
**채널이 하나도 빠지지 않았을 때만** 그 말을 한다. `else` 다.

즉 **다섯 채널 중 둘로 만들었고 게다가 폴백이 썼다** 는, 가장 의심해야 할 경우가
정확히 **폴백을 알려 주지 않는 유일한 경우**다. 경고가 필요한 바로 그때 사라진다.

두 사실을 한 문장으로 합치는 `summariseSnapsReportOutcome` 을 공유 모듈에 두고
**두 라우트 모두** 그것을 쓰게 했다 — 같은 질문에 다시 다르게 답할 수 없도록.
어느 쪽이든 참이면 경고 톤이고, 이름을 부르지 못한 채널 수는 `외 N건` 으로 붙는다.

변이 6개 전부 예상대로 — 원결함 복원(엔진 공지를 대체), 엔진 공지 삭제, 채널이 빠진
보고서를 성공으로 표시, 못 부른 채널 수 누락, 빈 경고를 채널로 계수, 그리고 대조군.

프런트엔드 `tsc` 가 이번에도 두 번 잡았다 — `targetPlatformLabel` 의 좁은 유니온이
`strictFunctionTypes` 아래에서 대입되지 않는 것, 그리고 import 누락. 둘 다 고쳤고
snaps 프런트엔드 오류는 0건이다.

**기존 정적 가드 둘이 이 리팩터링을 잡았다.** 하나는 `announceResult(` 호출 수를,
다른 하나는 핸들러 본문 안의 `'제외'` 문자열을 요구했다. 둘 다 "직접 하거나, 공유
리더에 위임하거나" 로 넓히고 공유 리더 자신을 검사하게 했다.

**그 과정에서 가드 하나가 물지 않는 것을 발견했다.** 결과를 알리는 생성기가 셋에서
넷으로 늘었는데 임계값은 `< 3` 그대로였다 — 보고서 알림 하나를 통째로 지우는 변이가
그대로 통과했다. **임계값이 개수를 따라가지 않으면, 대상이 늘어난 순간 가드가
느슨해진다.** `< 4` 로 올리고 넷이 무엇인지 주석에 적었다. 가드 변이 4개 전부
예상대로.

## 132. 느슨해진 가드 찾기 — 그리고 제 측정이 두 번 틀렸다

131번에서 나온 계열을 검증기 전체에 적용했다: **개수를 따라가지 않는 임계값.**
지키는 대상이 셋에서 넷으로 늘었는데 임계값이 `< 3` 에 머물면, 아무도 손대지 않았는데
가드가 느슨해진다. 하나를 지워도 통과한다.

`if (X < N)` 형태를 전부 뽑으니 약 30곳. 그중 `indexOf` 의 `< 0` 검사와, 패턴이
깨졌을 때 실패하라고 일부러 느슨하게 둔 바닥(`files.length < 20`,
`handlers.length < 40`, `known.size < 8`, `checked < 5`, `pairs < 1`)을 빼면
**세는 가드는 21곳**이다. 전부 지금 개수와 맞춰 봤다.

**진짜로 느슨한 것은 하나였다.**

```
assertSupportedPlatforms   임계값 2   실제 3   <- 하나를 지워도 통과
```

가드 메시지는 여전히 "both /video/attach-to-draft and /card-news/attach-to-draft"
라고 적혀 있었다. 그런데 변환 정규화기에 세 번째 호출이 추가되어 있었고, 그 주석은
이렇게 말한다 — *"The card news and video paths already refuse that by name; so does
this one."* 호출자가 늘어난 순간 가드가 그만큼 느슨해졌다. `< 3` 으로 올리고 셋이
무엇인지 메시지에 적었다.

**제 측정이 두 번 틀렸고, 두 번 다 코드가 옳았다.**

1. `...damaged` 와 `...ragWarnings,` 가 0건으로 나왔다 — 제가 **엉뚱한 파일**에서
   셌다. 가드는 `data-dir-health.ts` 와 `content-transform.service.ts` 를 읽는데
   저는 컨트롤러를 봤다. 실제로는 둘 다 2건, 정상.
2. `groupMetrics` 의 null-prototype 맵이 3건으로 나와 느슨해 보였다 — 제가 **고정
   900자 창**으로 잘라 다음 메서드 `chartSeries` 의 맵까지 삼켰다. 가드 자신은 이미
   다음 메서드 경계로 자르고 있고, **그 주석에 정확히 그 함정이 적혀 있다**:
   *"A fixed 900 character window ran past the end of groupMetrics into
   chartSeries... so this counted three and stayed green."* 제가 그 함정을 그대로
   다시 밟았다.

세 번째로 같은 실수다(전에는 40줄 창, 600자 창). **고정 크기 문맥 창은 쓰지 않는다 —
경계로 자른다.**

변이 3개 전부 예상대로 — 옛 임계값이 놓치던 세 번째 호출 제거, 첨부 라우트 하나
제거, 그리고 대조군(호출부 지역변수 개명).

## 133. 고정 크기 문맥 창 — 제 실수를 검증기에서 근본적으로 없앴다

이 세션에서 같은 실수를 세 번 했다(40줄 창, 600자 창, 900자 창). 132번에서 세 번째로
밟고 나서, **검증기 자신의 고정 창**을 전부 세어 봤다.

```
고정 창 26곳
  그중 메서드 선언에 앵커를 잡고 경계로 자르지 않는 것 8곳
```

그 8곳이 실제로 메서드를 넘어가는지 쟀다.

```
assertRenderJobBelongsToOrg  창 1600  메서드 1113  +487  -> @Post('/shorts-maker/...')
countBy                      창  900  메서드  720  +180  -> private dedupe(
vector store search          창 2600  메서드 2114  +486  -> async listExamples(
normalizeSummary             창 1800  메서드 1671  +129  -> private normalizeConversionSignals(
pixelleRuntimeHealth / cosine / importSources               경계 안
```

**일곱 중 넷이 남의 메서드를 읽고 있었다.** 지금 당장 거짓 통과를 내고 있지는
않았다(넷 다 경계로 자른 뒤에도 통과한다) — 잠재된 위험이었다. 하지만 이 파일에는
그 위험이 현실이 된 기록이 이미 있다. `groupMetrics` 가드의 주석이다:

> A fixed 900 character window ran past the end of groupMetrics into
> chartSeries... so this counted three and stayed green.

`methodBody(source, at, fallback)` 를 넣고 넷을 전부 경계 기준으로 바꿨다. 다음
선언(`private`/`public`/`protected`/`async`/`@`/`get `/`set `)에서 자른다.

**주장하지 않고 보여 줬다.** `countBy` 의 `Object.create(null)` 을 **옆 메서드로
옮기고** 가드를 두 번 돌렸다.

```
bounded window   -> exit 1  caught
old fixed window -> exit 0  MISSED - the blindness
```

변이 3개 예상대로 — 이웃으로 옮기기, `search()` 의 비교가능 플래그를 파일 안에
이름만 바꿔 남기기, 그리고 대조군(주석 수정은 실패하면 안 됨).

**제 실수도 두 번 더 나왔다.** (1) 첫 변이가 가드가 실제로 요구하는 것(`comparable`)이
아니라 제가 그럴 거라고 생각한 것(`sharesStem`)을 건드려서 살아남았다 — 변이는 가드가
**말하는 것**을 겨눠야 한다. (2) heredoc 이 또 이스케이프를 먹어 스크립트가 깨졌다.
이 세션에서 네 번째다. **내용이 있는 스크립트는 heredoc 으로 쓰지 않는다.**

## 134. 돈을 쓰는 스위치만 문서에서 빠져 있었다

제품 코드 쪽에서 결함이 잘 안 나와서, 아직 한 번도 보지 않은 표면을 봤다 —
**설정**. 코드가 읽는 환경 변수와 `.env.example` 이 선언하는 것을 양쪽에서 뽑아
차집합을 냈다.

```
읽지만 문서에 없음: SNAPS_API_URL, SNAPS_DEEPSEEK_CONFIRM,
                    SNAPS_PIXELLE_DURATION, SNAPS_PIXELLE_PLATFORM,
                    SNAPS_PIXELLE_SOURCE_TEXT
문서에 있지만 안 읽음: SNAPS_AGENCY_REVIEW_EMAIL, SNAPS_GENERIC_OAUTH,
                       SNAPS_INBOX_CLEAR_CONFIRM
```

**"안 읽음" 쪽은 제 탐지기의 맹점이었다.** `SNAPS_INBOX_CLEAR_CONFIRM` 은
PowerShell 스크립트가 `$env:` 로 읽는데 저는 `.ts/.tsx/.mjs/.js` 만 훑었다. 확인하고
넘어갔다 — 결함 아님.

**진짜는 반대쪽이다.** 라이브 실행을 막는 확인 스위치가 셋 있다.

```
SNAPS_PIXELLE_CONFIRM      렌더를 실제로 돌린다      .env.example 에 있음
SNAPS_NAVER_CAFE_CONFIRM   실제로 글을 올린다        .env.example 에 있음
SNAPS_DEEPSEEK_CONFIRM     유료 API 를 호출한다      없음
```

**셋 중 유일하게 돈을 쓰는 것만 빠져 있었다.** `.env.example` 을 읽는 운영자는 렌더와
게시를 어떻게 막는지는 배우지만, 유료 모델 호출을 어떻게 막는지(또는 켜는지)는 배울
수 없다. 형제 목록이 하나를 빠뜨린 계열이고, 이번에는 운영자용 설정 파일에서 나왔다.

Pixelle 스모크의 나머지 손잡이 셋(`PLATFORM`/`DURATION`/`SOURCE_TEXT`)도 같은 이유로
빠져 있어 함께 넣었다 — `SMOKE_ID` 는 있고 나머지는 없었다.

가드는 **이름을 나열하지 않는다.** 라이브 스모크 네 개에서 `SNAPS_*CONFIRM` 을 뽑아
전부 `.env.example` 에 있는지 본다. 셋 미만이면 "패턴이 깨졌다" 고 스스로 실패한다.

변이 5개 전부 예상대로 — 유료 스위치 삭제, 카페 스위치 삭제, Pixelle 스위치 삭제,
스위치 패턴이 아무것도 매치하지 않음, 그리고 대조군(문서의 기본값 변경은 통과해야 함).

## 135. 컨테이너에 닿지 않는 설정 — 이번엔 결함이 없었다

134번에 이어 설정 표면의 나머지 절반을 쟀다: **런타임이 읽는 것이 컨테이너에
도달하는가.** 코드가 읽는데 compose 가 넘기지 않는 변수는 이미지 안에서 기본값으로
조용히 떨어진다 — 운영자가 `.env` 에 넣어도 컨테이너는 못 본다.

**여기서 제 탐지기가 또 틀렸다.** 134번의 첫 스윕에서 compose 열이 전부 `-` 로 나와
"compose 가 아무것도 안 넘긴다" 처럼 보였는데, 제 정규식이 `.env` 모양(`NAME=`)만
찾고 YAML 모양(`NAME:`)을 안 봤기 때문이다. 고쳐서 다시 재니:

```
런타임이 읽는 snaps 설정 27개
compose 가 넘기지 않는 것: 없음
compose 가 넘기는데 런타임이 안 읽는 것: 없음
SNAPS_DEBUG_TRANSFORM 만 주석 처리 — 의도된 결정
```

**결함 없음.** 양방향으로 완전하다. 이 세션에서 탐지기가 틀린 네 번째이고, 네 번 다
코드가 옳았다. *음성 결과는 탐지기를 증명하기 전까지는 결과가 아니다.*

그래도 이 불변식은 지킬 값이 있어서 가드로 남겼다 — 새 설정이 추가될 때 compose 에
넣는 것을 잊으면 깨진다. **주석 처리된 키는 통과한다**: 적어 둔 결정이지 누락이
아니다. 설정을 15개 미만으로 찾으면 "패턴이 깨졌다" 고 스스로 실패한다.

변이 6개 전부 예상대로 — 렌더러 URL·저장 위치·모델 타임아웃이 컨테이너에 닿지 않게
하기, 설정 패턴 무력화, 그리고 대조군 둘(주석 처리는 통과, 값 변경도 통과).

`snaps-pixelle-video` 의 8000 포트 노출도 확인했다 — compose 주석에 이유와
`127.0.0.1:8000:8000` 대안까지 이미 적혀 있다. 결정 목록에 그대로 둔다.

## 136. 백로그 질문에 답이 나왔다 — Prisma 모델은 연결되지 않은 것이 맞다

사용자가 오래 전에 남긴 항목: *"Postiz 신규 Prisma 모델의 실제 서비스/컨트롤러 연결
여부 확인."* 이번 회차에 측정했다.

스키마의 51개 모델을 전부 Prisma 클라이언트 호출과 대조했다.

```
51개 모델 중 어디서도 쿼리되지 않는 것 22개
  그중 snaps 소유: SnapsStyleExample, SnapsMetricSnapshot, SnapsReport
  나머지는 mastra_* (외부 프레임워크 테이블)와 이 포크에서 쓰지 않는

TypeScript 쪽에서 이름이 비슷해 걸린 것들(`SnapsReportRequest`,
`SnapsReportGeneratorService`, `SnapsStyleExampleDto`)은 **접두사만 같은 무관한
타입**이다. 진짜 호출부는 없다.

**그리고 이것은 이미 문서화된 의도된 상태다.** `docs/snaps-completion-audit.md:46`:

> A schema audit confirms these three models have no Prisma client call site
> anywhere in `libraries/` or `apps/` — that is the intended state, since every
> snaps service persists to JSON under `SNAPS_DATA_DIR` ... and the models exist
> only as the migration target.

`npm run verify:snaps:db` 가 모델과 손으로 쓴 SQL 헬퍼를 양방향으로 대조한다:
`verify-snaps-db-contract-ok models=3 columns=32 indexes=15`.

**백로그 항목의 답: 연결되어 있지 않고, 그것이 설계다.** 결정 목록에서 내린다.

다만 **아무것도 그 상태를 지키지 않고 있었다.** 위험한 방향은 반대쪽이다 — 누군가
모델 하나를 쿼리하기 시작하면 JSON 파일이 여전히 진짜 저장소인 채로 테이블에 두 번째
사본이 쌓이고, 둘이 어긋나도 아무 데서도 오류가 나지 않는다. 양방향으로 못박았다:

- 세 모델이 Prisma 로 쿼리되면 실패한다(`저장소를 통째로 옮기든지, 둘 다 두든지`).
- 새 `Snaps*` 모델이 쿼리도 없고 감사 문서에도 없으면 실패한다 — 만들어지고 절대
  채워지지 않는 테이블이 이유도 없이 생기는 것이다.

변이 4개 예상대로 — 모델을 쿼리하기 시작, 모델 패턴 무력화(배치), 그리고 삽입형
변이 둘은 배치 러너가 거부해서(새 텍스트가 옛 텍스트를 포함) 직접 돌렸다:
문서 없는 새 모델 추가 → `exit 1 caught`, 대조군(스키마 주석) → `exit 0 passed`.

또 하나 배웠다: 대조군으로 `sourceUrl` 필드 이름을 바꿨더니 실패했는데, 그것은 이
가드가 아니라 **DB 계약 검증기**가 스키마와 SQL 헬퍼의 열 이름 불일치를 잡은 것이다.
대조군은 **다른 가드도 건드리지 않는** 변경이어야 한다.

## 137. X 는 글자를 세지 않는다 — 한국어 우선 제품에서 280은 틀린 숫자였다

결정 목록에 오래 있던 항목: *"X 의 `maxLength: 280` 은 한국어 가중 계산에서는 ~140
일 수 있다. 확인할 자격 증명이 없다."* 자격 증명이 필요 없다는 것이 이번에 확인됐다 —
가중치는 공개된 결정적 규칙이고, **산술로 검증된다.**

```
declared maxLength = 280
한국어 본문을 그 규칙으로 자르면  = 280자
X 가 세는 값                     = 479 units
X 가 받는 값                     = 280 units
따라서 X 는 거절한다              = true

같은 규칙을 영어에 적용하면       = 280자 = 280 units   (정상)
280 units 에 실제로 들어가는 한국어 = 164자
```

**영어에는 맞고 한국어에는 틀린 규칙이다.** 그리고 이 제품은 한국어 우선이다.
증상은 워크스페이스의 경고가 아니라 **게시 시점의 거절**이다 — 운영자가 가장 늦게,
가장 나쁜 형태로 알게 되는 실패다.

고침은 `maxLength` 를 140 으로 바꾸는 것이 아니다(그러면 영어 게시물이 절반으로
잘린다). X 만 **가중 한도**를 선언하고, 그 한도로 자른다.

- `text/weighted-length.ts` — `snapsWeightedLength`, `snapsClampToWeight`.
  Latin·일반 문장부호는 1, 나머지는 2(공개된 twitter-text 가중치, config v3).
  자르기는 `snapsClampText` 에 위임한다 — "문자를 쪼개지 않는다" 는 구현을 두 벌
  두지 않기 위해서다.
- 규칙 타입에 `weightedLimit?: number`. **열 개 플랫폼 중 X 에만 있다.**
- 변환 서비스의 두 경로(모델 답변, 결정적 폴백)가 그 한도로 자른다.
- 경고가 이유를 말한다: `한글은 두 자로 셉니다`. 이유 없이 140에서 끊기면 운영자는
  임의의 절단으로 읽는다.

**기존 테스트 하나가 옛 동작(280자)을 고정하고 있었다.** 이제 가중 길이가 280
이하인지, 전부 한글이면 140자에서 멈추는지, 그리고 경고가 세는 방식을 설명하는지를
본다.

**변이 하나가 살아남아 테스트를 강화했다.** `snapsClampText` 를 `text.slice` 로
바꿔도 통과했다 — 제 단언이 "고아 서로게이트 없음" 까지만 봤기 때문이다. 코드포인트
경계는 `slice` 도 지킨다. 차이가 드러나는 것은 **자소 군집**이다. ZWJ 로 이어진 가족
이모지를 예산 안쪽에 두니, `slice` 는 반쪽 가족을 남기고 `snapsClampText` 는 통째로
뺀다. 그 케이스를 넣으니 잡힌다.

변이 5개 예상대로(대조군 포함). 삽입형 변이 하나는 배치 러너가 거부해서 뺐다.

**남은 가정:** 라이브 X 호출로 확인하지 못했다. 근거는 공개된 가중치 알고리즘이다.
틀렸다면 증상은 "한국어 게시물이 필요보다 짧게 잘린다" 이고, 지금 상태인 "게시
시점에 거절된다" 보다는 낫다. 결정 목록에서는 내리되 이 가정을 여기 남긴다.

## 138. 137번의 형제 둘 — 고치고 바로 확인했다

137번에서 변환 경로를 가중 계산으로 바꿨다. 이 세션에서 가장 많이 결함을 낳은 계열이
*"이름 목록을 고치고 형제를 빠뜨린다"* 이므로, **제가 그 실수를 저지르기 전에**
플랫폼 한도를 재는 모든 곳을 세었다. 셋이었고 하나만 고쳐져 있었다.

```
transform/content-transform.service.ts   고침 (137번)
cardnews/card-news-variant.builder.ts    글자로 셈  <- 캡션이 X 에서 거절된다
agent/command-planner.service.ts         글자로 셈  <- 준비 완료라고 보고한다
```

- **카드뉴스 캡션**: X 변형 캡션을 280자로 잘랐다. 한국어면 479 units 라서 게시 시점에
  거절된다. 변환 경로의 형제다 — X 에게 캡션은 곧 본문이다.
- **에이전트 준비도 행**: `200/280자` 처럼 **글자**를 280과 비교했다. 한국어 200자는
  X 가 400으로 세어 반드시 거절하는데 **"준비 완료"로 보고**했다. 이제 세는 방식까지
  적는다: `400/280자 분량 (한글 2자)`. 이유 없이 막히면 운영자는 임의의 제한으로 읽는다.

기존 테스트 둘이 옛 동작(X 280자)을 고정하고 있어 가중 불변식으로 바꿨다.

가드는 **모양**으로 본다: `rule.maxLength` 로 텍스트를 재는 파일은 `rule.weightedLimit`
도 다뤄야 한다. 그리고 가중 한도를 선언한 규칙이 **정확히 하나**여야 한다 — 다른
플랫폼에 붙이면 한국어 게시물이 이유 없이 절반이 된다.

**변이 하나가 두 번 살아남았다.** "모든 플랫폼에 가중치 적용" 변이를 200자 Threads
로 잡으려 했으나 통과했고(200 < 1500), 300자로 올려도 통과했다(600 < 1500). Threads
한도가 1500이라 **글자로는 통과하고 units 로는 초과하는 길이**가 있어야 구별된다 —
800자(800자 vs 1600 units)에서 잡힌다. 숫자를 재지 않고 고르면 테스트는 통과하는
모양만 갖춘다.

변이 5개 예상대로(대조군 포함).

## 139. 네 번째 자리는 제 가드 자신이 놓쳤다 — 게시 직전의 마지막 관문

138번에서 "플랫폼 한도를 재는 곳은 셋" 이라고 세고 셋을 고쳤다. **넷이었다.**

`schedule/publishing-payload.builder.ts` 는 `rule?.maxLength` 로 읽는다 — **옵셔널
체이닝** 때문에 제 grep(`rule\.maxLength`)에도, 138번에 제가 쓴 가드의 파일 목록에도
걸리지 않았다. 그리고 이 파일은 **게시 직전의 마지막 관문**이다:
`/snaps/schedule-variants` 로 직접 들어온 변형은 변환도 카드뉴스 빌더도 거치지 않아,
여기서 자르지 않으면 그대로 플랫폼에 간다.

두 곳이었다.

- 본문 클램프: 280**자**로 잘라 X 에 넘겼다 → 560 units → 거절.
- 해시태그 접미사: `body.length + suffix.length > maxLength` 로 여유를 쟀다.
  **글자로는 들어가고 units 로는 넘치는** 태그가 붙어, 모든 검사를 통과한 게시물이
  거절됐다.

둘 다 플랫폼이 세는 단위로 재도록 고쳤다.

**가드를 이름 목록에서 트리 순회로 바꿨다.** 138번의 가드는 파일 셋을 나열했고, 그
자체가 이 가드가 대체하려던 바로 그 약점이었다. 이제 snaps 트리를 걸어서
`rule?.maxLength` 형태까지 잡고, 네 자리 미만이면 "패턴이 깨졌다" 고 실패한다.
기존 해시태그 가드도 가중 측정을 받아들이도록 넓혔다.

기존 테스트 하나가 X 본문 280자를 전제로 하고 있어 고쳤다 — 이제 예산을 정확히 채우는
본문(한글 140자 = 280 units)으로 태그 탈락 동작을 본다. 그리고 **호출자가 직접 준
변형**이 이 관문에서 잘리는지 보는 테스트를 새로 넣었다.

**변이 하나는 무효였다.** `maxLength = rule?.weightedLimit ?? rule?.maxLength` 를
`rule?.maxLength` 로 되돌리는 변이가 살아남았는데, **X 는 두 값이 모두 280 이라
수치가 같다.** 관측 가능한 차이가 없으므로 테스트의 결함이 아니라 변이의 결함이다.
다만 잠재적 취약점은 남는다 — 누군가 X 의 `maxLength` 를 560("280 units = 한글
560자")으로 바꾸면 두 값이 갈라진다.

변이 3개 예상대로(대조군 포함), 1개 무효.

## 140. 모든 것을 지키는 파일들만 아무도 지키지 않고 있었다

137~139번 변경을 라이브로 회귀 확인했다 — `verify:snaps:cardnews-deepseek` rc=0,
템플릿 3개 전부 통과, 이모지 캡션 온전, per-platform clamps ok.

그러다 **라이브 검증기 자신의 단언이 낡아 있는 것**을 봤다.

```

verify-snaps-cardnews-deepseek.ts:241  published.length      <= rule.maxLength
```

X 는 units 로 센다. 이제 캡션이 140자로 잘리므로 **140 <= 280 은 가중 클램프가
망가져도 통과한다** — 이 스모크가 잡아야 할 바로 그것을 못 잡는다. 둘 다 플랫폼이
세는 단위로 재도록 고쳤다.

**그리고 더 큰 것이 나왔다.** 그 수정을 타입 검사하려고
`npm run verify:snaps:spec-types` 를 돌렸더니 **이미 오류 두 개가 있었다** —
`verify-snaps-controller.ts` 의 508행과 574행, **118~119번에서 제가 쓴 줄들**이다.

왜 지금까지 안 잡혔나: **preflight 가 그 프로젝트를 타입 검사하지 않는다.**

```
preflight 가 타입 검사하는 프로젝트: libraries, backend, frontend, orchestrator,
                                     commands, extension, sdk  (7개)
타입 검사하지 않는 것: tsconfig.snaps-spec.json
  = snaps.core.spec.ts + scripts/verify-snaps-*.ts
```

**다른 모든 것을 지키는 파일들이, 아무도 지키지 않는 유일한 부분이었다.** 오류 둘을
고치고(그 과정에서 스펙의 생성자 인자 누락 하나도 더 나왔다), preflight 에 단계를
추가했다.

가드가 **자기 주석에 속았다.** 처음엔 preflight 파일에 `tsconfig.snaps-spec.json` 이
언급되는지만 봤는데, 제가 그 위에 쓴 설명 주석이 바로 그 파일명을 담고 있어서
**단계를 통째로 지워도 통과**했다. 인자 형태(`"tsconfig.snaps-spec.json",`)를 보도록
바꾸니 잡힌다.

변이 3개 예상대로(대조군: 단계 이름 변경은 통과해야 함).

## 141. 아무도 돌리지 않는 검증기 둘

140번이 "검증하는 것들을 아무도 검증하지 않는다" 였으니 같은 질문을 한 번 더 밀었다:
**존재하지만 아무도 돌리지 않는 검증기가 있는가.**

`verify:snaps*` 30개를 preflight/final 이 실제로 호출하는 파일과 대조했다.

```
preflight 나 final 이 닿지 않는 것 5개
  verify:snaps:cardnews-deepseek    의도적 — 유료, SNAPS_DEEPSEEK_CONFIRM 로 잠김
  verify:snaps:core-deepseek        의도적 — 같은 이유

verify-snaps-shorts-maker-contract-ok routes=2 verbs=3 bypassGuards=3 publishedPorts=0

## 142. 답글이 필요한 댓글이 조용히 `other` 로 들어간다

검증 도구 쪽이 마르기에 제품으로 돌아왔다. 피드백 분류기를 **한국 사람이 실제로 쓰는
방식**으로 쓴 댓글 24개에 태워 봤다.

```
7/24 가 운영자가 부를 이름과 달랐다
** other      want=praise      전혀 문제없었어요, 잘 쓰고 있습니다
** praise     want=complaint   좋긴 한데 배송이 너무 느려요
** other      want=praise      잘 봤습니다
** other      want=complaint   품질이 기대 이하네요
** other      want=complaint   사진이 흐릿하게 나왔어요
** other      want=spam        가입하면 수익 보장! 클릭하세요
** other      want=praise      구매했는데 만족합니다
```

**일곱 개가 전부 답글을 잃는 방향으로 틀렸다.** 특히 두 번째는 가장 나쁜 형태다 —
운영자가 칭찬으로 읽고 넘어가고, 그 안의 불만은 영원히 답을 못 받는다. 불만 검사가
칭찬보다 **먼저** 오는데도 그렇게 된 이유는, 그 문장의 불만 어휘가 속도 표현뿐이고
속도 표현이 목록에 하나도 없었기 때문이다.

고친 것:

- **불만**: `기대 이하`, `느[리려림립린렸]`, `아쉽`, `불만`. 한국어 활용형을
  빠뜨리면 안 된다 — `느리` 만 넣었더니 `배송이 느립니다` 가 안 잡혔다(느리+ㅂ니다
  → 립). 테스트가 그 자리에서 잡았다.
- **칭찬**: `만족`, `유익`, `잘\s*봤`, `잘\s*쓰`. **맨 `잘` 은 넣지 않는다** —
  `잘 안 돼요`, `잘못 배송됐어요` 가 칭찬이 되고, 그건 이 수정이 막으려는 바로 그
  방향이다. 연어(collocation)로만 넣고 테스트로 고정했다.
- **스팸**: 링크가 없어도 홍보 어휘가 셋 이상이면 스팸이다.
  `가입하면 수익 보장! 클릭하세요` 는 셋인데 링크가 없어 `other` 였다. 하나만으로는
  안 된다 — `무료 배송이라 좋아요` 는 칭찬이다.

```
고친 뒤: 1/24 불일치 (`사진이 흐릿하게 나왔어요` — 불만 어휘가 하나도 없는
         서술형이라 키워드 분류기가 잡을 수 있는 종류가 아니다)
```

변이 8개 전부 예상대로 — 속도 표현 되돌리기, `기대 이하` 빼기, 칭찬을 불만보다 먼저
검사하기, `만족`/`잘 봤` 빼기, **맨 `잘` 을 칭찬으로 넣기**, 링크 없는 홍보를 스팸에서
빼기, 홍보 한 단어로 스팸 판정하기, 그리고 대조군.

## 143. 142번이 만든 불일치 — 그리고 그 옆에 원래 있던 것

142번에서 분류기의 불만 목록을 넓혔다. 같은 파일 스무 줄 아래에
`detectConversionSignals` 가 **같은 판단을 두 번째로** 내리고 있다. 형제를 바로
확인했다.

```
품질이 기대 이하네요       sentiment=complaint      signals=-
배송이 느립니다            sentiment=complaint      signals=-
조금 아쉽네요              sentiment=complaint      signals=-
불만이 좀 있어요           sentiment=complaint      signals=-
좋긴 한데 배송이 너무 느려요 sentiment=complaint      signals=-
```

**불만이라고 분류한 댓글 다섯 개에 complaint-risk 신호가 하나도 없다.** 운영자의 할
일 목록은 신호로 만들어지므로, 불만은 답글 프롬프트 없이 지나간다. **142번이 만든
불일치다** — 한쪽 목록만 넓혔다.

그리고 그 옆에 **원래 있던 것** 하나가 같이 드러났다.

```
광고문의 드립니다          sentiment=collaboration  signals=-
광고 문의 드립니다          sentiment=collaboration  signals=collaboration
```

한쪽은 `광고\s*문의`, 다른 쪽은 **리터럴 공백**의 `광고 문의` 였다. 띄어쓰기 없이
쓴 제안은 감정은 협업인데 신호가 없다.

**복사본을 하나 더 만들지 않고 패턴을 공유했다.** `SNAPS_COMPLAINT_PATTERN` 과
`SNAPS_COLLABORATION_PATTERN` 을 모듈 상수로 두고 두 메서드가 같은 것을 읽는다.
부정 가드(`문제(?!\s*없)`)도 이제 한 곳에만 있다.

측정 결과 아홉 케이스 전부 감정과 신호가 일치한다.

변이 5개 전부 예상대로 — 신호 쪽이 자기 복사본으로 되돌아가기, 공백 때문에 갈라지기,
부정 가드 잃기, 142번에서 추가한 단어들 잃기, 그리고 대조군(공유 상수 개명).

**기존 정적 가드 둘이 이 리팩터링을 잡았다.** 하나는 `문제(?!` 를 `classify()` 본문
안에서 찾았고(이제 상수에 있다), 다른 하나는 **두 벌**이 각각 부정 가드를 갖기를
요구했다. 둘 다 "복사본 둘, 또는 공유 패턴 하나" 를 받아들이도록 넓혔다.

**그리고 새로 넣은 가드가 제 주석에 속았다.** 공유 상수 이름이 몇 번 나오는지 세었는데,
탐지기 쪽 주석의 `see SNAPS_COMPLAINT_PATTERN` 이 한 번으로 계산되어 **탐지기가 자기
정규식으로 되돌아가도 통과**했다. 이름이 아니라 **호출**(`.test(`)을 세도록 바꾸니
잡힌다. 이 파일에서 가드가 산문에 속은 것이 **세 번째**다.

## 144. 산문에 속는 검사 — 세 번 당했으니 표면 전체를 쟀다

가드가 코드가 아니라 **주석**에 만족한 것이 세 번이다(140, 143번 그리고 123번의
600자 창). 계열이 확실하니 표면 전체를 쟀다.

`expectContains(파일, 문자열)` 이 찾는 문자열이, **그 파일의 주석을 지운 뒤에도**
남아 있는가.

```
911개 needle 검사 — 주석에만 있는 것: 0개
```

**탐지기를 먼저 증명했다.** 주석에만 있는 문구(`says the opposite`)를 찾는 검사를
하나 끼워 넣으니 정확히 그것만 보고한다(912개 중 1개). 그 뒤에야 0을 믿었다.

손으로 쓴 `expectCustom` 쪽도 같은 방식으로 보려 했으나, `read(...)` 를 지역변수에
담는 형태만 따라갈 수 있어 **1,200여 검사 중 5개**만 해석됐다. 0/5 는 깨끗하다는
뜻이 아니라 **보이지 않는다**는 뜻이므로, 그렇게 적는다.

일회성 프로브로 끝내지 않고 **검증기 자신의 가드로 넣었다.** 새 `expectContains` 가
추가될 때마다 이 실수를 다시 할 수 있고, 이 검사는 911개를 한 번에 본다. 200개
미만이 잡히면 "패턴이 깨졌다" 고 스스로 실패하고, 해석된 needle 이 200개 미만이어도
실패한다 — 보지 못하는 것을 통과로 보고하지 않기 위해서다.

삽입형 변이 둘은 배치 러너가 거부해 직접 돌렸다:
주석에만 있는 검사 추가 → `exit 1 caught`, 호출 패턴 무력화 → `exit 1 caught`.

**세 번의 실수에서 나온 규칙:** 가드는 이름이 아니라 **모양**을 봐야 한다 —
`X.test(`, `"key",`, `?.field` 처럼 코드에만 나타나는 형태. 이름만 세면 그 이름을
설명하는 주석이 검사를 대신 통과시킨다.

## 145. 네 계층이 각자 지킨다고 적어 둔 것을, 끝에서 끝까지 확인했다

저장소·빌더·클램프·게시 페이로드가 **각각 자기 주석에** "작성자의 줄바꿈을 지킨다"
고 적어 두었다. 그런데 **네 계층을 통째로 지나가는 확인은 없었다.** 운영자가 입력
상자에 친 문단 구분이 게시물에서 사라지면 읽는 사람이 보는 글이 달라지는데, 조용히
달라진다.

열 플랫폼 전부에 다문단 한국어 본문을 태웠다.

```
threads/instagram/youtube/tiktok/xiaohongshu/naver-blog/
naver-cafe/kakao-talk/linkedin/x   전부  breaks=7  blankRuns=3
```

**결함 없음. 열 개 전부 그대로 나간다.**

**음성 결과를 믿기 전에 프로브를 깨뜨려 봤다.** 페이로드 빌더에서 본문을
`replace(/\s+/g, ' ')` 로 평탄화하니 `breaks 7 -> 2`, `blankRuns 3 -> 1` 로 떨어진다
(남은 하나는 해시태그 앞 구분이다). 프로브가 실제로 본다.

**확인한 성질을 테스트로 남겼다.** 일회성 측정으로 끝내면 다음 변경 때 다시 확인해야
하고, 이 성질은 네 계층에 걸쳐 있어 어느 한 곳만 고쳐도 깨진다. 열 플랫폼 전부에
대해 문단 구분 3개, 단일 줄바꿈 유지, 그리고 **빈 줄이 세 줄 이상 연속되지 않는지**
까지 본다.

변이 5개 전부 예상대로 — 본문 평탄화, 문단을 한 줄로 축약, 빈 줄을 늘리기, 해시태그를
본문에 붙이기, 그리고 대조군.

**대조군이 한 번 깨졌다.** 지역변수를 개명하면서 사용처 일곱 곳 중 다섯만 바꿨더니
컴파일이 안 됐다. 대조군은 *의미가 같은 변경*이어야 하고, 절반만 바꾼 개명은 그냥
깨진 코드다.

## 146. 이모지가 잘리는지 끝에서 확인했다 — 그리고 제 프로브가 처음엔 아무것도 안 쟀다

124번에서 텍스트 클램프 여덟 곳을 자소 단위로 바꿨다. 그 체인의 **끝**을 확인했다:
이모지가 든 본문이 게시 페이로드까지 가서 반쪽으로 잘리지 않는가, 열 플랫폼 전부.

**첫 프로브는 0건을 보고했고, 그건 아무것도 재지 않은 결과였다.** 이모지가 든 문구를
반복해서 긴 본문을 만들었는데, **어느 플랫폼의 한도도 이모지 위에 떨어지지 않았다.**
클램프를 `slice` 로 바꾸는 변이를 넣어도 결과가 그대로였다.

이모지는 **뿌리는 게 아니라 놓아야 한다.** 플랫폼마다 예산 직전 위치를 계산해 그
자리에 이모지를 두었다(X 는 가중 계산이라 별도로).

```
기준선                 열 플랫폼 전부  loneSurrogates=0
클램프를 slice 로 바꾸면  열 중 아홉에  loneSurrogates=1
```

X 만 살아남는데, 가중 클램프가 코드포인트 경계를 스스로 계산하기 때문이다 — 139번에서
확인한 것과 같은 이유다.

**기준선은 깨끗하다.** 124번의 여덟 군데가 끝까지 유지된다. 성질을 테스트로 남겼다.

**그리고 변이 하나가 살아남아 죽은 분기를 찾아냈다.** `snapsClampText` 에는 경로가
둘이다 — `Intl.Segmenter` 가 있을 때와 없을 때. 여기 Node 에는 Segmenter 가 있으므로
**두 번째 경로는 한 번도 실행되지 않는다.** 통째로 지워도 전체 스위트가 통과했다.
그 경로는 Segmenter 가 없는 런타임을 위한 것이고, 거기가 바로 깨져도 아무도 모를
자리다.

모듈이 세그먼터를 첫 호출에 캐시하므로, `jest.isolateModules` 로 `Intl.Segmenter` 를
지운 채 새로 읽어 그 경로를 태우는 테스트를 넣었다. 서로게이트 쌍 한가운데를 자르지
않는지, 들어가는 쌍은 온전히 남기는지, 그리고 **정말 그 경로를 타고 있는지**(세그먼터가
가려졌는지)까지 본다.

변이 4개 전부 예상대로 — 클램프를 코드 단위로, 서로게이트 폴백 제거, 게시 백스톱이
클램프를 그만두기, 그리고 대조군(주석 수정).

## 147. 환경 때문에 실행되지 않는 분기 — 그리고 파괴적 동작의 관문

146번에서 "이 환경에서는 절대 실행되지 않는 분기" 를 하나 찾았으니, 같은 모양을
snaps 소스 전체에서 훑었다.

```
환경 능력 검사 8곳
  clamp-text.ts        Intl.Segmenter 유무      -> 146번에서 테스트 추가
  snaps-workspace.shared.ts  typeof window        <- 남은 하나
  나머지 6곳은 navigator.clipboard 호출 (분기 아님)
```

남은 하나가 `confirmOperatorAction` 이다.

```ts
export const confirmOperatorAction = (message: string) =>
  typeof window !== 'undefined' && window.confirm(message);
```

**파괴적이거나 되돌릴 수 없는 동작 12곳이 이것을 관문으로 쓴다** — 원문 삭제, 받은
반응함 전체 비우기, 라이브 채널에 답글 게시. 정적 검사는 호출부가 있는지 확인한다.
**그런데 이 함수가 무엇을 답하는지는 아무것도 확인하지 않았다.**

두 분기 다 중요하다. 서버 렌더 패스에는 `window` 가 없고, 거기서 안전한 답은
**거절**이다 — 확인 없이 진행하는 것이 아니라.

네 경우를 고정했다: window 없음 → 거절, 운영자가 아니오 → 거절, 예 → 진행,
그리고 **운영자가 본 문구가 호출자가 준 문구인지**. 마지막으로 "정말 window 를 지운
채로 재고 있는지" 를 확인하는 가드-the-가드를 붙였다 — 진짜 window 가 남아 있으면
첫 번째 경우가 엉뚱한 이유로 통과한다.

변이 5개 전부 예상대로 — 서버 패스가 확인 없이 진행, 아예 묻지 않고 진행, 항상 거절,
문구를 고정 문자열로 바꾸기, 그리고 대조군(파라미터 개명).

## 148. 관문이 있는지가 아니라, **빠진 데가 있는지**

147번은 `confirmOperatorAction` 이 무엇을 답하는지를 고정했다. 나머지 절반은
반대 질문이다 — **관문을 거치지 않는 파괴적 동작이 있는가.**

세 워크스페이스에서 지우거나 되돌릴 수 없는 호출을 전부 뽑았다.

```
9건 중 7건 관문 있음
관문 없는 2건: /snaps/inbox/import, /snaps/inbox/import-post-comments
```

**둘 다 제 탐지기의 과매칭이었다.** 워크스페이스 복원(`/snaps/import`)을 잡으려고
`'/import'` 를 포함 검사했는데 인박스의 **추가** 임포트가 같이 걸렸다. 진짜 파괴적인
`/snaps/import`(백업 복원, 기존 레코드를 밀어낼 수 있다)는 관문이 있다.

**결함 없음.** 일곱 건 전부 먼저 묻는다.

그래도 "새 파괴적 동작이 관문 없이 추가되는" 것은 실제 위험이고 검사가 싸므로
가드로 남겼다. 파괴적의 정의는 `DELETE` 이거나 `publish-reply` 이거나 워크스페이스
복원이고, **추가형 임포트 둘은 이유와 함께 명시적으로 제외**했다 — 모든 임포트마다
물으면 운영자는 확인창을 습관적으로 넘기게 된다.

핸들러 경계까지 거슬러 올라가 관문을 찾는다. **고정 줄 수 창을 쓰지 않는다** — 앞
함수의 확인을 읽고 이 함수를 "관문 있음" 으로 세는 것이 이 세션에서 세 번 나온
실수다.

변이 4개 예상대로 — 원문 삭제가 묻지 않기, 인박스 비우기가 묻지 않기, 호출 패턴
무력화, 그리고 대조군.

**대조군을 두 번 잘못 골랐다.** 확인 문구를 바꾸는 것으로 하려 했더니 실패했는데,
이 가드가 아니라 **기존 `expectContains` 가 그 문장을 통째로 고정**하고 있기 때문이다
(두 문구 모두). 대조군은 *다른 가드도 건드리지 않는* 변경이어야 한다 — 136번에서
같은 실수를 했다. 관계없는 주석 수정으로 바꿔 통과를 확인했다.

## 149. 아무도 읽을 수 없는 속도의 나레이션

쇼츠 대본은 장면마다 나레이션과 시간대를 갖고, 그 둘이 맞아야 한다. 한국어 나레이터는
초당 대여섯 음절을 읽는다. 결정적 대본을 실제 원문으로 태워 음절/초를 쟀다.

```
15초 요청, 4장면
  scene 1  3.0s  25음절  8.3/s  **
  scene 2  3.0s  32음절 10.7/s  **
  scene 3  3.0s  30음절 10.0/s  **
  scene 4  6.0s  16음절  2.7/s
```

**앞의 셋은 사람이 낼 수 없는 속도이고, 마지막은 시간이 남는다.** 시간이
**내용과 무관하게** 균등 분할되기 때문이다. 렌더러는 읽을 수 없는 타임라인을 받는다.

두 가지를 고쳤다.

1. **장면 시간이 말할 양을 따라간다.** 음절 수에 비례해 초를 나눈다. 남는 초는
   **최대 잔여(largest remainder)** 로 배분한다 — 처음엔 "말이 많은 장면부터" 줬는데,
   그러면 정확 배분 3.64인 장면이 바닥값 3에 머물러 8.3/s 로 남고 이미 6.0인 장면이
   더 받는다. **잘려 나간 소수부가 초를 빚진 곳을 가리킨다.**
2. **어떤 분배로도 읽을 수 없으면 그렇게 말한다.** 103음절을 15초에 넣으면 장면을
   나누기 전에 이미 초당 6.9다. 경고를 대본에 실어 보낸다:
   `대본이 15초에 비해 깁니다. 한국어 나레이션 속도로 약 18초가 필요합니다.`

```
고친 뒤 30초: 3.57 / 3.56 / 3.33 / 3.20  (편차 0.37)
고친 뒤 15초: 여전히 빠르지만 경고가 나간다
```

**라우트에서 경고가 사라질 뻔했다.** `videoScript` 는 `{ ...script, warnings }` 로
정규화 경고를 덮어쓴다. 대본이 자기 경고를 갖게 되었으므로, 요청에도 문제가 있는
바로 그때 페이싱 경고가 사라진다. 두 목록을 **합치도록** 고쳤다.

**변이 하나가 살아남아 임계값을 측정으로 정했다.** "편차 1음절 미만" 으로는 두 배분
방식을 구별하지 못한다(0.37 vs 0.80 둘 다 통과). 30초에서 두 방식이 갈라지는 지점이
0.5 이므로 거기에 두고, 두 방식의 실제 숫자를 주석에 적었다. **임계값을 재지 않고
고르면 테스트는 통과하는 모양만 갖춘다** — 138번과 같은 교훈이다.

변이 7개 전부 예상대로 — 균등 분할 복귀, 남는 초를 잘못 배분, 모든 장면 동일 가중,
경고 삭제, 경고가 필요한 시간을 말하지 않음, 나레이터가 두 배 빠르다고 가정, 그리고
대조군.

## 150. 슬라이드에서 잘린 글자를 아무도 말해 주지 않는다

149번이 "시간에 맞지 않는 나레이션" 이었으니, 같은 질문을 카드뉴스에 했다 —
**슬라이드에 안 들어가는 글자는 어떻게 되는가.**

결정적 덱은 여유 있게 들어간다(6줄 예산에 1~3줄). 문제는 **모델이나 호출자가 준
덱**이다. `/card-news/generate` 는 `deck.slides` 를 직접 받는다.

```
192자 본문 -> 6/6줄, 마지막 줄이 "…" 로 끝난다 (나머지는 사라짐)
응답의 warnings: (렌더러가 만드는 것 없음)
```

렌더러는 **자기가 자른 것을 아무 데도 말하지 않는다.** 변형 빌더는 자기가 자른 캡션을
보고하고(`captionTrims`), 변환 서비스는 모델 답변을 자른 것을 보고한다. **렌더러만
조용히 자른다.** 이미지를 열어 본 사람은 말줄임표를 보지만, 응답을 읽는 사람은 모른다.

`wrapText` 가 마지막 줄에 붙이는 말줄임표를 되읽어 어느 부분이 잘렸는지
(`'heading' | 'body'`) 슬라이드에 실어 보내고, 라우트가 그것을 한국어 경고로 바꾼다:
`슬라이드 2의 본문이(가) 길어 이미지에서 잘렸습니다.`

**경고를 합치는 자리를 또 조심해야 했다.** `/card-news/generate` 는
`normalized.warnings` 만 반환했다. 원문을 자르면서 슬라이드도 자른 실행은 둘 다
말해야 하므로 이어 붙였다 — 149번의 라우트와 같은 형태다.

변이 5개 전부 예상대로 — 조용히 자르기로 복귀, 잘린 본문을 못 알아채기, 잘린 제목을
못 알아채기, **자르지 않은 슬라이드까지 잘렸다고 보고하기**, 그리고 대조군.

**기존 테스트 셋이 이 변경을 잡았다.** `buildSlideSvg` 를 스파이로 감싸 반환값을
문자열로 쓰고 있었는데, 이제 `{ svg, trimmed }` 를 돌려준다. 세 스파이가 답을 풀어
쓰도록 고쳤다 — 내부 시그니처를 바꿨을 때 테스트가 알려 주는 것이 정상 동작이다.

## 151. 저장이 저장을 지운다 — 그리고 아무 말도 하지 않는다

149번과 150번이 "내용을 조용히 잃는 계층" 이었으니, 그 목록을 끝까지 훑었다. 자를 수
있는 계층은 여덟이고 일곱은 보고한다. 남은 하나가 **저장소 상한** 이다.

가져오기 경로는 116번 이후로 `dropped` 를 보고한다. **의도적인 저장 경로는 보고하지
않는다.**

```
원문 500건을 채운 뒤 한 건 저장
  before=500  after=500   한 건이 사라짐
  saveSource() 의 답: 새 레코드뿐, 지워진 것에 대한 말 없음
```

상한에 도달한 운영자는 **저장할 때마다 저장해 둔 원문을 하나씩 잃고, 그 사실을 듣지
못한다.** RAG 스타일 예시도 같다.

둘 다 지워진 개수와 한국어 경고를 답에 싣는다:
`저장 원문이 상한 500개에 도달해 가장 오래된 1개를 지웠습니다. 필요한 원문은 먼저
내보내세요.`

**활동 로그는 일부러 그대로 뒀다.** 굴러가는 로그이고 거의 모든 라우트가 여기에
쓰므로, 쫓겨남을 보고하면 거의 모든 요청에 잡음이 붙는다. 코드에 이유를 적었다.

**프로브가 만든 착시 하나를 확인하고 넘어갔다.** 처음엔 쫓겨난 것이 **가장 최근**
레코드로 보였다. 제가 씨앗 배열을 오래된 것부터 넣었기 때문이고, 저장소는 파일 순서를
그대로 쓴다(`list()` 는 정렬하지 않는다). 제품이 만드는 배열은 최신이 앞이므로 실제로
쫓겨나는 것은 가장 오래된 것이다. 결함 아님.

변이 5개 전부 예상대로 — 두 저장 경로가 각각 조용히 지우기로 복귀, **지우지 않았는데
지웠다고 보고하기**, 개수를 실제 대신 상수로 답하기, 그리고 대조군.

## 152. 151번이 서비스에서 멈춰 있었다

151번에서 저장 경로가 무엇을 지웠는지 답하게 만들었다. **그 답을 읽는 쪽을 바로
확인했다** — 122번에서 배운, *한 층 위에서 되돌아가는지* 보는 습관이다.

```ts
const saved = await response.json();
...
toast.show('원문을 snaps 라이브러리에 저장했습니다.');   // saved.warning 은 버려진다
```

**두 저장 핸들러 모두 응답을 읽고 경고를 버린다.** 서비스에서 멈춘 수정은 수정이
아니다 — 운영자는 여전히 저장할 때마다 원문을 하나씩 잃고 여전히 "저장했습니다" 를
읽는다.

공유 리더 `describeSnapsSaveOutcome` 로 합쳤다. 다른 리더들과 같은 모양이다.

**RAG 쪽에서 하나가 더 나왔다.** `announceStyleExampleSaved` 는 임베딩 없이 저장된
경우를 경고하는데, **그 분기에서 곧바로 반환**한다. 예시가 임베딩 없이 저장되면서
**동시에** 상한을 넘겨 오래된 예시를 지웠다면, 앞의 것만 말하고 뒤의 것은 사라진다.
131번과 같은 형태 — *두 사실 중 하나만 말하는 분기*. 이제 둘 다 싣는다.

변이 5개 전부 예상대로 — 상한 경고 버리기, 예시 자신의 경고 버리기, 잃은 저장을
성공으로 표시, 빈 문자열을 경고로 취급, 그리고 대조군.

## 153. 123번이 고치지 않은 세 번째 경로 — 주 예약 경로

"한 가지만 말하고 반환하는 분기" 가 두 번(131, 152) 나왔으니 계열로 훑었다.

**첫 스윕은 35건을 보고했고 거의 전부 가드 절이었다** — 입력이 없으면 말하고 멈추는
것은 옳다. 그 시점에는 다른 할 말이 없다. 결함이 된 형태는 **결과에 대한 통지**가
같은 결과의 두 번째 사실을 말하기 전에 반환하는 것이다. 응답을 읽은 **뒤**만 보도록
좁혔다.

```
5건
  shorts: 대본이 없거나 있거나 — 진짜 양자택일 (3건)
  snaps-workspace.tsx:1402  createDrafts  <- 이것
```

123번에서 카드뉴스와 쇼츠의 첨부 경로를 `describeSnapsAttachResult` 로 고쳤는데,
**주 예약 경로(`/snaps/schedule-variants`)를 빠뜨렸다.** 거기에 그대로 남아 있었다:

```ts
if (!created) {
  const reason = warnings[0] || '연결된 채널에 게시물이 생성되지 않았습니다.';
  toast.show(reason, 'warning');
  return;
}
```

**제가 형제를 빠뜨린 것이다.** 그것도 셋 중 가장 많이 쓰이는 경로를. 두 가지가
같이 틀려 있었다 — `PostsService.createPost` 가 뒷받침하지 못하는 주장을 하고,
빌더 경고를 첫 줄만 보여 준다.

공유 리더를 쓰되 **문구는 이 경로의 것을 유지**했다. 카드뉴스와 쇼츠는 만들어지는
게시물에 무언가를 *첨부*하고, 이 경로는 게시물 자체를 *만든다*. 판단은 같고 동사만
다르므로, 선택적 `phrase` 콜백을 받는다.

변이 4개 전부 예상대로 — 호출자 문구 무시, 첨부 문구를 전부 대체, ready-but-empty
분기가 주 경로에 적용되지 않게 하기, 그리고 대조군(파라미터 개명).

## 154. 도망갈 구멍을 막았다 — 그리고 가드가 이름에 묶여 있었다

153번에서 형제 하나를 빠뜨린 것이 드러났으니, **왜 가드가 그것을 잡지 못했는지** 를
봤다. 제가 123번에 쓴 가드는 이렇게 되어 있었다:

```
직접 읽거나(`?.scheduled` + `if (!created)`),
공유 리더에 위임하거나 — 둘 중 하나면 통과

**그 "둘 중 하나" 가 세 번째 파일을 세 회차 동안 살려 두었다.** 두 경로를 변환한 뒤

정리하면서 죽은 코드도 나왔다 — `created` 지역변수가 선언만 남고 아무도 읽지 않는다
(`noUnusedLocals` 가 꺼져 있어 컴파일러도 조용했다). 응답 타입에 `schedulable` 도
빠져 있었다. 공유 리더가 런타임에는 읽지만 타입만 보면 없는 것처럼 보인다. 둘 다
고쳤다.

**그리고 대조군이 깨졌다 — 가드 탓이었다.** 지역변수 `outcome` 을 `attachOutcome`
으로 바꾸는, 의미가 같은 변경이 실패했다. 가드가 `outcome\.tone === 'warning'` 을
**이름째로** 요구했기 때문이다. **가드가 이름에 묶이면 안전한 리팩터링이 막힌다** —
이 세션에서 여러 번 남의 코드에서 지적한 형태를 제가 쓴 가드가 갖고 있었다.
`\w+\.tone === 'warning'` 으로 바꾸니 대조군이 통과한다.

변이 3개 전부 예상대로 — 주 경로가 다시 스스로 판단, 워크스페이스가 리더의 판단을
쓰지 않음, 그리고 대조군(지역변수 개명).

## 155. 가드가 이름에 묶였고, 그다음엔 메시지에 속았다

154번에서 제 가드 하나가 지역변수 이름에 묶여 있던 것이 드러났으니, **전부**

## 156. RAG 검색이 점수의 근거를 거짓으로 말하고 있었다

침묵하는 실패를 찾으려고 snaps 서비스의 `catch` **48개** 를 전부 훑었다. 34개가
아무것도 기록하지 않지만 대부분은 주석으로 의도를 밝힌 의도적 폴백이고,
`report-generator` 는 이미 `provider: 'rule-fallback'` 로 라벨을 단다. 그런데 RAG
에서 진짜가 나왔다.

벡터 스토어는 히트마다 `comparable = cosine !== undefined` 를 계산해 **정렬에 쓴 뒤
버렸다**(`.map(({ comparable, ...hit }) => hit)`). 그래서 소비자 둘이 각자
**되유도**했다:

```ts
matchedBy: hit.embedding ? 'embedding' : 'keyword'   // 컨트롤러 572, 프롬프트빌더 44
```

**이건 조건의 절반이다.** 코사인은 (1) 질의도 임베딩됐고 (2) 두 벡터 길이가 같을
때만 나온다. `rag.service.search()` 는 임베딩 호출이 던지면 질의 임베딩을
`undefined` 로 만든다 — Ollama 가 죽어 있는 **평범한** 경로다. 그러면 전부 토큰
점수로 매겨지는데, 저장된 임베딩이 있는 예시는 전부 `'embedding'` 으로 라벨이
붙는다. 프런트는 이미 `matchedBy === 'keyword' ? '키워드 일치' : '유사도'` 를
그리고 있었으니, 화면에는 **키워드 1.00 위에 "유사도 1.00"** 이 찍혔다. 임베딩
모델을 바꿔 차원이 달라져도 같은 거짓말을 한다.

고친 방향: **분기를 실제로 탄 쪽이 말한다.** `SnapsStyleSearchHit` 에
`matchedBy: 'embedding' | 'keyword'` 를 추가하고 `comparable` 에서 직접 내보낸다.
컨트롤러와 프롬프트 빌더는 되유도를 그만두고 `hit.matchedBy` 를 그대로 쓴다.

변이 3/3 예상대로 — 저장 여부로 되유도하기, 길이 불일치를 0으로 뭉개기, 그리고
대조군(`comparable` 플래그 개명)은 통과. 기존 테스트 하나가 제 변경을 잡았다:
`ragHits` 고정값이 손으로 만들어져 `matchedBy` 가 없었다. 고정값을 실제 `search()`
반환 모양으로 맞추면서 **임베딩을 가졌지만 keyword 로 매겨진 히트** 를 넣어
오히려 강해졌다 — 정확히 오라벨되던 경우다.

가드도 붙였다: 스토어는 `matchedBy: comparable ?` 형태를 유지해야 하고, 두 소비자는
`hit.matchedBy` 를 써야 하며 `\w+\.embedding ? 'embedding'` 을 다시 쓰면 실패한다.

교훈: **어떤 분기를 탔는지는 그 분기를 탄 코드만 안다.** 대리 지표로 되유도하면
설명은 맞고 코드는 틀린 상태가 조용히 남는다 — 주석 둘 다 조건을 정확히 적어 놓고
있었다.

## 157. 156번은 하나가 아니라 부류였다 — 양쪽 끝이 없는 계약

156번의 모양은 이것이다: **프런트가 읽는 필드를 API 가 보내지 않는다.** 타입이
`matchedBy?:` 라 아무도 불평하지 않았다. 같은 것이 더 있는지 훑었다 — snaps
프런트 타입의 선택적 필드 중 UI 가 실제로 읽으면서 서버 어디에서도 만들어지지
않는 것. **2개** 가 나왔고 둘 다 `SnapsShortsHandoff` 의 `scriptPlatform`,
`videoResult` — 서버가 아니라 localStorage 로 오가는 값이라 **오탐**이다.
`sendAgentShortsToMedia()` 가 둘 다 쓴다. (정직한 음성)

그런데 그 오탐이 더 나은 표적을 가리켰다. 작업대 사이 인계는 전부 localStorage 를
지나므로 **양 끝을 맞춰 보는 것이 아무것도 없다.** 그리고 이 프로젝트는 이미 그
대가를 치렀다 — `sendAgentCardNewsToMedia()` 의 docstring 이 기록한다:

> 카드뉴스 작업대는 쓰인 날부터 `snapsCardNewsHandoffKey` 를 읽었고 **아무도 쓰지
> 않았다** — 에이전트에게 카드뉴스를 시킨 운영자는 버튼이 아무 일도 안 하는 것을
> 봤다.

한쪽은 "버튼이 먹통", 반대쪽(156번)은 "화면에 틀린 라벨". 지금 두 키는 서로
맞는다(측정함: 카드뉴스 writer 6필드 ⊇ reader 5필드, 쇼츠 writer 8 ⊇ reader 7).
어긋난 적이 있으니 가드를 붙였다:

- 모든 `snaps*HandoffKey` 는 writer 와 reader 가 **둘 다** 있어야 한다.
- reader 가 읽는 필드는 writer 가 쓰는 **최상위** 키에 포함돼야 한다.
- 쓰기만 하고 안 읽는 필드(`createdAt`)는 허용 — 화면을 틀리게 만들지 않는다.

중첩을 최상위로 착각하지 않도록 중괄호 깊이로 키를 뽑고, **파싱된 지역변수 이름에
묶지 않았다**(155번 규칙) — `handoff` 라고 못박으면 개명이 "아무도 안 읽는 인계"로
보이고, 그게 바로 이 가드가 소리쳐야 할 단 하나이기 때문이다. 대신
`const X = JSON.parse(` 에서 이름을 읽고, 그 형태가 없으면 **판단을 포기하는 대신
실패한다**.

변이 4/4 예상대로 — writer 가 `scriptPlatform` 을 빼기, 카드뉴스 writer 를 잃기(=
과거 실제 결함), `videoResult` 를 한 단계 중첩시키기, 그리고 대조군(파싱 지역변수
`handoff` → `carried` 개명)은 통과.

## 158. 경고는 이미 있었고, 한 겹 위에서 증거가 지워지고 있었다

이번에는 직감 대신 **측정으로 표적을 골랐다** — snaps 라이브러리 전체 커버리지를
재서 테스트가 건드리지 않는 파일을 찾았다. `analytics-metric.mapper.ts` 가
**statements 0%, branch 0%, functions 0%** — 496개 테스트 중 단 하나도 지나가지
않는다. 순수 함수인데 아무도 보지 않는다.

읽어 보니 결함이 있었다. 매퍼는 프로바이더 값을 이렇게 바꿨다:

```ts
const numeric = Number(value ?? 0);
return Number.isFinite(numeric) ? numeric : 0;
```

**이건 리포트의 `numeric()` 과 같은 코드다** — 쌍둥이 구현이 한 겹 위에서 먼저
돈다. 그리고 리포트에는 이미 이런 것이 있다:

```
private countUnreadableValues(metrics: unknown[])
  "지표 값 N개를 숫자로 읽지 못해 0으로 계산했습니다"  ← actionItems 맨 앞
```

주석까지 정확하다 — *"`metricValue: "1,200"` 는 대시보드가 보여 주는 모양이고
운영자가 붙여 넣는 모양이다. 구분 기호를 떼는 것은 로케일에 대한 추측이다. 읽지
못했다고 말하는 것은 추측이 아니다."*

**그런데 연동 분석 경로에서는 그 경고가 영구히 장님이었다.** 매퍼가 먼저 `'1,200'`
을 유한한 `0` 으로 바꿔 버리니, 리포트가 볼 때는 멀쩡한 숫자 0 이고 unreadable
개수는 0 이며 리포트는 그 값을 **사실로 진술한다**. `AnalyticsData.data` 는
`Array<{ total: string }>` 이고 프로바이더들은 실제로 `current?.followerGains?.
organicFollowerGain` 같은 옵셔널 체인을 넣는다.

고친 방향: **변환은 리포트만 한다.** 매퍼는 값을 쓰인 그대로 넘긴다
(`preserveMetricValue`). `SnapsMetricInput.metricValue` 는 `number | string`.
없는 값은 다른 모든 경로와 같이 0, 원시값이 아니면 문자열화해서 "읽을 수 없음"으로
도착한다 — **숫자를 지어내지 않는다.**

**라이브 스모크가 제 변경을 잡았다.** `verify-snaps-services.ts` 가
`total: '7'` 에 대해 `metricValue === 7` 을 단언하고 있었다 — 타입은 통과하지만
런타임에 깨진다(`number|string` 을 `number` 와 비교하는 건 합법). 의도적으로
`=== '7'` 로 고치고, `'1,200'` 이 그대로 도착하는지 단언을 **추가**했다. 정적
가드 하나도 옛 메시지에 못박혀 있어 같이 갱신했다.

변이 3+3/6 예상대로 — 매퍼가 다시 변환, 매퍼가 구분 기호를 떼고 숫자를 추측,
`SnapsMetricInput` 이 다시 `number` 로 좁아지기는 모두 잡히고, 대조군 둘(헬퍼
개명, **주석에 `Number()` 를 쓰기**)은 통과. 뒤의 대조군은 155번의 `codeOnly()` 가
제 몫을 한다는 증거이기도 하다.

교훈: **경고가 있다고 경고가 도달하는 것은 아니다.** 증거를 지우는 코드가 한 겹
위에 있으면 경고는 조용히 0을 보고한다 — 그리고 그 코드는 보통 같은 일을 하는
쌍둥이다.

## 159. 모델 응답의 JSON 을 찾지 못해 규칙 결과를 내주고 있었다

커버리지로 계속 표적을 골랐다. `deepseek.client.ts` **branch 52.8%**, 그중
`extractJson` 은 통째로 미측정. 먼저 **재려고** 현재 구현을 그대로 복사해 모델이
실제로 내놓는 15가지 모양에 돌렸다:

```
4 of 12 realistic shapes fail today
  fenced with prose after the fence   FAILS
  fenced as javascript                FAILS
  top-level array                     FAILS
  array with prose after              FAILS
```

원인 셋:
- `.replace(/```$/i,'')` 는 **맨 끝에 붙은** 펜스만 뗀다. 모델이 닫는 펜스 뒤에
  한 문장 덧붙이면 그대로 남는다.
- `(?:json)?` 은 `json` 태그만 안다. ```` ```javascript ```` 는 `javascript` 가
  남는다.
- `{` 첫 위치 ~ `}` 마지막 위치로 자르면 **최상위 배열이 대괄호를 잃는다** —
  `[{"a":1},{"b":2}]` → `{"a":1},{"b":2}`.

`JSON.parse` 가 던지면 호출자는 "모델이 실패했다"로 읽고 결정론적 경로로 답한다.
**멀쩡한 모델 응답이 버퍼에 있는 채로 운영자는 규칙 결과를 받는다.**

**그리고 쌍둥이가 있었다.** `ollama.client.ts` 에 바이트 단위로 동일한 사본. 둘
중 하나만 고치면 나머지는 틀린 채 남는다 — 게다가 **중요한 쪽은 Ollama** 다.
DeepSeek 만 `response_format: json_object` 를 요구받고 Ollama 는 아니라서, 펜스와
꼬리 문장은 Ollama 쪽에서 훨씬 자주 나온다. 그래서 두 사본을 고치는 대신
`snaps/ai/extract-json.ts` **하나**로 뽑고 둘 다 import 한다. 새 구현은 15/15 통과.

**변이에서 배운 것 — 어느 부분이 실제로 일을 하는가.** 처음 5개 중 1개가
살아남았다: 닫는 펜스 탐색을 없애도 객체는 여전히 파싱된다. 이제 펜스 분기가
early-return 이 아니라 **fall-through** 라서 뒤의 중괄호 스캔이 구해 주기 때문이다.
그래서 진짜 구분되는 모양을 찾아 넣었다:

- 펜스 뒤 문장이 **중괄호를 품을 때**(`예: {"b":2}`) — 닫는 펜스를 못 찾으면
  스캔이 그 예시까지 삼킨다.
- **태그 붙은 배열**(```` ```js\n["a","b"] ````) — 중괄호가 없으니 스캔이 구해 줄
  수 없다. 태그 패턴이 홀로 일을 하는 유일한 모양이다.

두 모양을 넣고 나서야 **5/5 예상대로** — 닫는 펜스 앵커 되돌리기, `json` 만
인식하기, 배열 처리 제거, 태그를 `[^\n]*` 로 탐욕스럽게 만들기(한 줄 펜스 페이로드를
통째로 먹는다) 모두 잡히고, 대조군(위치 지역변수 개명) 통과.

**부수 발견 — 제 `codeOnly()` 가 이 파일에서 틀렸다.** 구분자로 비우는 방식이라
**백틱을 담은 정규식 리터럴**(`/^```[a-z]*\n?/`)을 템플릿 문자열로 보고 같이
비운다. 가드 하나가 그것 때문에 오작동했다. 이 파일은 주석만 벗기도록 바꾸고,
한계를 `codeOnly()` 문서에 적었다 — **다음 사람이 같은 곳에서 넘어지지 않도록.**

기존 가드 하나도 제 변경을 잡았다: 원시 `.slice()` 금지. 두 slice 는 길이가 아니라
**검색해서 찾은 ASCII 구분자 위치**라 서로게이트를 쪼갤 수 없으므로, 가드가 스스로
요구하는 방식대로 `positions` 에 의도적으로 등록했다.

## 160. 썸네일을 쇼츠 영상으로 올리고 있었다

커버리지 표적 셋째. `short-video.service.ts` **branch 59.17%**, 미측정 구간의
대부분이 Pixelle 응답에서 자산과 잡 아이디를 **뒤져 찾는** 재귀 함수 둘이다.
Pixelle 배포마다 응답 모양이 달라서 키를 훑는 구조인데, 아무도 그 훑기를 본 적이
없다.

먼저 **쟀다** — 구현을 복사해 그럴듯한 응답 4가지에 돌렸다:

```
3 of 4 payloads resolve to the wrong asset or job
  nested assets, thumbnail listed first   video WRONG https://x/t.png
  user object before the job id           job   WRONG u-99
  poster url nested under preview         video WRONG https://x/frame.jpg
```

결함 셋:

1. **레벨 우선 탐색.** 깊이 1의 일반적인 `url` 이 깊이 2의 정확한 `download_url`
   을 이긴다.
2. **영상과 썸네일이 같은 `url` 을 본다.** 객체 리터럴이 먼저 나열한 쪽이 이긴다 —
   `{assets: {thumbnail:{url}, video:{url}}}` 이면 **PNG 가 쇼츠 영상이 된다.**
   운영자는 정지 이미지를 영상으로 붙이고 화면은 완료라고 말한다.
3. **`id` 가 키 목록 끝에 있고 트리 전체를 뒤진다.** `{user:{id:'u-99'},
   task:{id:'j-3'}}` 이면 `u-99` 를 폴링한다.

고친 방향:
- 키 우선, 트리 전체. 한 키를 payload 전체에서 찾고 없을 때만 다음 키로.
- 각 자산 슬롯이 **상대의 파일 타입을 거부** 한다(`accept` 술어로, 거부하면 멈추지
  않고 **계속 찾는다**). 형제까지 같이 — 영상 슬롯만 고치면 썸네일 슬롯이 남는다.
- 잡 아이디는 전용 해석기: 명시적 키 → payload 자신의 `id` → `job|task|result|
  data|output` 이름의 컨테이너 아래 `id`. `user.id` 는 잡이 아니다.

**변이가 다시 "무엇이 실제로 일하는가" 를 가르쳤다.** 처음 5개 중 2개 생존:
- 레벨 우선으로 되돌려도 통과 — `accept` 가 이미지 거부로 구해 주기 때문. 키 우선이
  홀로 일하는 모양은 **확장자 없는 서명 URL**(`preview?token=abc`)이다. 거부할
  근거가 없으니 키 순서만이 답을 정한다. 추가.
- 썸네일의 영상 거부도 통과 — 구분되는 모양이 없었다. **포스터가 mp4 인 경우**
  (일부 파이프라인은 움직이는 미리보기를 만든다)를 추가했다. `<img>` 로는 못 보니
  **썸네일 없음이 정직한 답** 이다.

두 모양을 넣고 **5/5 예상대로** — 레벨 우선 되돌리기, 영상의 이미지 거부 제거,
썸네일의 영상 거부 제거, `id` 를 키 목록에 되넣기 모두 잡히고, 대조군(`accept`
매개변수 개명) 통과.

가드는 네 가지 형태와 함께 **두 패턴이 서로의 여집합인지** 를 본다 — 한쪽 목록에만
확장자를 추가하면 그 슬롯이 다시 열린다.

교훈 반복: **변이가 살아남으면 테스트가 약한 것이 아니라, 그 코드가 홀로는 일하지
않는다는 뜻일 수 있다.** 어느 쪽인지는 구분되는 모양을 찾아봐야 안다.

## 161. 고치고 나서 옆 필드를 안 봤다 — 이번엔 그 파일 자신의 주석이 증인

커버리지 표적 넷째. `feedback-inbox.service.ts` **branch 65.81%**. 미측정 구간에서

- 카운트는 위아래로 묶는다. 모델이 키워드가 놓친 발생을 찾아 **올릴 수는 있다**

**제 첫 기대값이 틀렸다.** 카운트 1을 기대했는데 2가 나왔다. 이 파일의 doctrine 은

**변이 하나가 살아남아 제 주석이 검증되지 않았음을 드러냈다.** "공백 정규화"를

대신 **정규화된 인용문을 반환** 하게 바꿨다 — 운영자가 문장 중간에 줄바꿈이 든
인용문을 보면 응답이 그렇게 쓰인 줄 안다. 그러고 나서 **5/5 예상대로** — 천장 제거,
모델이 인용문을 쓰기, 재줄바꿈 인용문 거부, 모델 줄바꿈 그대로 노출 모두 잡히고
대조군(헬퍼 개명) 통과.

교훈: **한 필드를 고쳤으면 같은 객체의 형제를 보라.** 그리고 **주석에 쓴 성질은
테스트로 증명하라** — 안 그러면 그 문장은 다음 사람에게 거짓말이 된다.

## 162. 거절은 지켰고 요청은 안 지켰다 — 주석이 세 판째 거짓말

161번의 교훈("형제를 보라")을 이번엔 **체계적으로** 적용했다. 모델 출력과

정직한 음성 둘:

- `scheduleType` 은 OR 이라 명령이 발행을 요청하면 모델이 `draft` 라 해도 예약이

그런데 `command-planner.service.ts` 에서 진짜가 나왔다. 이 파일은 필드마다 "운영자가

const includeCardNews = this.refuses(command, SNAPS_CARD_NEWS_WORDS)

  ? payload.includeCardNews                 // 요청: 모델이 이김
  : fallback.includeCardNews;
```

그 바로 위 주석은 이렇게 적혀 있다 — **"거절은 요청만큼이나 명시적이다."** 코드는
세 판째 그 문장을 지키지 않고 있었다.

측정: `카드뉴스 만들어줘` 에 모델이 `includeCardNews: false` 를 답하면 카드뉴스가

채널은 이미 보호돼 있었다(`namedPlatforms`) — **만들지 말지** 만 안 지켜졌다.

고침: `refuses → false`, `asksFor → true`, 그다음에야 모델. 둘 다.

**그리고 대조군이 기존 가드를 깼다.** `refuses` 와 `asksFor` 를 맞바꾸는(의미가
동일한 — `refuses()` 자체가 "단어가 있고 요청이 아님"이라 서로 배타적이다) 변경이
`'const includeCardNews = this.refuses('` 라는 **분기 순서에 못박힌 바늘** 을
깨뜨렸다. 155번에서 제 가드에 대해 배운 것이 남의 가드에도 있었다. 두 바늘을

차이다.

## 163. 남의 거절을 자기 것으로 읽었다 — 또 고정 크기 창

162번에서 `asksFor` 를 건드렸으니 그 함수 자체를 봤다. 거절 판정이 이렇다:

```ts
const after = command.slice(match.index + match[0].length, ... + 14);
return !/(만들지\s*마|빼고|빼줘|없이|제외|말고|...)/.test(after);
```

**키워드 뒤 14글자.** 이 프로젝트가 이미 세 번 당한 그 모양이다(40줄, 600자, 900자).
이번에는 창이 **다른 키워드의 거절** 을 삼킨다.

먼저 채널 탐지부터 쟀다 — 10개 전부 정상 감지(정직한 음성). `snapsTargetPlatforms`
를 기준으로 검사하는 테스트를 새로 넣어 잠갔다(채널을 추가하고 탐지기를 안 넣으면
실패한다).

그다음 `asksFor` 를 쟀다: **8개 중 3개가 남의 거절을 읽었다.**

| 명령 | 판정 | 실제 결과 |
|---|---|---|
| `인스타에 올리고 쇼츠는 빼줘` | 인스타 **거절** | 운영자가 지정한 단 하나의 채널이 빠지고 **기본 4채널로 발행** |
| `쇼츠로 만들고 카드뉴스는 빼줘` | 쇼츠 **거절** | 영상이 안 만들어짐 |
| `카드뉴스로 만들고 쇼츠는 없이` | 카드뉴스 **거절** | 카드뉴스가 안 만들어짐 |

첫 줄은 이 파일이 **이미 두 번 고친 바로 그 피해** 다(`엑스에 올려줘` → 기본 4채널).

고친 규칙: **거절은 자기 바로 앞 주제의 것이다.** 창 안에서 거절 표지보다 **다른
주제어가 먼저** 나오면 그 거절은 저쪽 것이다. 12개 사례 전부 통과.

이걸 하려면 `asksFor` 가 채널 이름을 알아야 해서, 채널 표를 `detectTargetPlatforms`
안에서 **모듈 스코프로 끌어올려** 둘이 같은 목록을 읽게 했다 — 사본 둘을 만들면
갱신을 잊는 쪽이 하필 `asksFor` 가 읽는 쪽이 된다.

**변이 하나가 또 "무엇이 일하는가"를 가르쳤다.** "채널을 주제 목록에서 빼기" 변이가
살아남았다 — 사례 중 **사이에 끼어드는 주제가 채널인** 것이 하나도 없었다.
`쇼츠로 만들고 인스타는 빼줘` 를 넣으니 **4/4 예상대로**.

교훈(세 번째 반복): **고정 크기 창은 이웃을 읽는다.** 그리고 **변이가 살아남으면
그 코드가 홀로 일하지 않거나 사례가 그 축을 안 건드린 것** — 어느 쪽인지 찾아야
한다.

## 164. 네 번 당한 모양을 기다리지 않고 전수조사했다

163번이 고정 크기 창 결함의 **네 번째** 였다. 다섯 번째를 기다리는 대신 **결정을

28개 중 27개가 결정을 내리고, 그중 **24개가 검증기 자신** 에 있었다. 이 파일은

## 166. AI 클라이언트가 타임아웃을 두 번 내고 있었다

커버리지로 돌아왔다. `ollama.client.ts` branch 68.67%, 미측정 구간에 재시도 로직이
있다:

```ts
try { return await this.fetchOnceWithTimeout(url, options, timeoutMs); }
catch (error) {
  const fallbackUrl = this.localhostIpv4FallbackUrl(url);   // localhost -> 127.0.0.1
  if (!fallbackUrl) throw error;
  return this.fetchOnceWithTimeout(fallbackUrl, options, timeoutMs);
}
```

재시도 자체는 정당하다 — Node 는 localhost 를 ::1 로 풀고 Ollama 는 IPv4 로
듣는다. 문제는 **어떤 실패에도** 재시도한다는 것이다. **타임아웃 포함.**

측정: 150ms 예산, 연결은 받고 응답하지 않는 소켓 → **시도 2회.** 즉 호출자가 정한
예산의 **두 배** 를 기다린다. `/health` 프로브가 "타임아웃을 순차로 지불한다"고
이미 고쳐진 바로 그 결함이 AI 클라이언트에 남아 있었다.

그리고 같은 자리에서 **사본 세 개** 가 나왔다. 공용 헬퍼 `snapsFetchWithTimeout`
이 이미 있는데(쇼츠메이커·Pixelle 이 쓴다) 두 AI 클라이언트가 각자 열두 줄을
복제해 두었다. 그 사본들은 공용 헬퍼가 가진 것 둘을 놓쳤다:

1. 마감 경과를 `"The operation was aborted"` 로 보고한다 — 호출자가 취소한 것처럼
   읽힌다.
2. 예산을 `Number(process.env.X || 기본값)` 로 읽는다. **`Number('30초')` 는 NaN
   이고 `setTimeout` 은 NaN 을 1ms 로 취급한다** — 오타 하나면 모든 AI 요청이 즉시
   중단된다. 공용 `snapsTimeoutMs` 가 바로 이걸 막으려고 존재한다.

고침: 두 클라이언트 모두 공용 헬퍼를 쓰고, 타임아웃 예산은 `snapsTimeoutMs` 로
읽는다. 헬퍼는 마감 오류에 `snapsTimedOut` 표식을 붙이고, Ollama 는 **표식이 있으면
재시도하지 않는다** — 문구가 아니라 표식으로 구분한다.

테스트 3개: 응답 없는 서버는 **1회**만 기다린다 / **연결 거부는 여전히 127.0.0.1
로 재시도한다**(재시도의 본래 목적이 살아 있는지) / **숫자가 아닌 타임아웃 환경변수는
무시된다.**

변이 4/4 예상대로 — 마감 후 재시도 복원, 원시 `Number()` 복원, 재시도 자체 제거,
그리고 대조군(catch 매개변수 개명) 통과.

교훈 반복: **공용 헬퍼가 생겼으면 기존 사본을 옮겨야 끝난다.** 사본은 헬퍼가 배운
것을 배우지 못한다.

## 170. 로딩 중인 버튼을 키보드로는 계속 누를 수 있었다

프런트로 옮겨 재귀적 결함 부류를 찾았다. 먼저 **정직한 음성 둘**:

- `useEffect` 는 snaps 컴포넌트 전체에 **4개뿐이고 전부 deps 가 비어 있다** —
  마운트 1회. 의존성 변화로 인한 응답 경합은 없다. (탐지기가 4개를 찾았으니
  눈먼 것이 아니다.)
- `eslint-disable` 없음.

그리고 **진짜**가 나왔다. 변형(POST/DELETE)을 하는 핸들러 28개 중 22개가 로딩
플래그를 세운다. 그런데 버튼은 `disabled=` 가 아니라 `loading=` 을 받는다. 공용
`Button` 을 열어 보니:

```tsx
className={clsx((props.disabled || loading) && 'opacity-50 pointer-events-none', ...)}
```

**`pointer-events-none` 는 마우스만 막는다.** 버튼은 여전히 포커스를 받고
`disabled` 속성이 없으므로 **Enter/Space 로는 계속 눌린다.** 즉 요청이 나가 있는
동안 키보드로 다시 제출할 수 있고, `createDrafts` 처럼 **예약 게시물을 만드는**
버튼이면 두 벌이 만들어진다. 스크린 리더에도 "비활성"으로 읽히지 않는다.

고침: `disabled={props.disabled || loading}` 한 줄. **버튼을 더 눌리게 만들 수는
없고 덜 눌리게만 만드는 변경** 이다.

**범위를 밝혀 둔다:** 이 파일은 snaps 전용이 아니라 앱 전체가 쓰는 공용 컴포넌트다
(`loading=` 사용처: snaps 32, 앱 전체 57). 상류 코어의 *복잡한* 동작 변경은 이
로그에서 계속 "결정 필요"로 남겨 왔지만, 이번 것은 한 줄이고 엄밀히 더 제한적이며
호출자 쪽 계약을 바꾸지 않아 직접 고쳤다. 되돌리기도 한 줄이다.

변이 3/3 예상대로 — `disabled` 제거, `loading` 만 빼기, 그리고 대조군(두 조건 순서
바꾸기) 통과.

**부수 — 제 도구가 세 번째로 같은 곳에서 넘어졌다.** `codeOnly()` 가
`'pointer-events-none'` 을 문자열이라고 비워서 가드가 오작동했다. 159·167번에도
같은 일이 있었고 그때마다 **그 자리에 즉석 strip 을 복사** 해 두었다. 이번엔
`commentsOnly()` 를 만들고 즉석 사본 2개를 거기로 옮겼다 — **제가 남의 코드에서
계속 찾아내던 바로 그 모양을 제 도구가 하고 있었다.** 규칙: 바늘이 문자열이나
정규식 안에 있으면 `commentsOnly`, 코드 형태면 `codeOnly`.

## 171. 가드가 죽은 설정을 살려 두고 있었다

170번 뒤에 "고친 것의 한 겹 아래"를 봤다 — `loading` 플래그 16종이 전부 각 동작의
것이라 버튼을 비활성화해도 막히는 범위가 달라지지 않는다. 정직한 음성. 오케스트레이터도
봤는데 snaps 코드는 문자열 하나뿐이다. 역시 음성.

그래서 운영자가 실제로 만지는 것을 쟀다 — **코드가 읽는 환경변수 vs 문서에 있는 것.**

- 코드가 읽는데 어디에도 없는 것: **2개**(`NAVER_CAFE_SUBJECT`,
  `NAVER_CAFE_CATEGORY` — 네이버 카페 스모크 입력). 문서화했다.
- 반대 방향이 진짜였다: **`.env.example` 에 있는데 아무 코드도 읽지 않는 것 1개** —
  `SNAPS_INBOX_CLEAR_CONFIRM="clear"`.

이건 더 나쁜 쪽이다. 운영자는 받은 반응함을 비우는 동작에 확인 관문을 걸었다고
믿는데 **아무것도 걸리지 않는다.** 형제 셋(`PIXELLE`, `DEEPSEEK`, `NAVER_CAFE`)은
각자 라이브 스모크가 읽고 거부한다. 이것만 읽는 곳이 없다.

확인해 보니 실제로 비우는 두 경로는 이미 안전하다 — 서비스 스모크는 임시 데이터
디렉터리와 고정 `smoke-org` 를 쓰고, 라우트는 프런트가
`confirmOperatorAction('...모두 비울까요?')` 로 묻는다. 그러니 이 스위치는 **처음부터
아무것도 지키지 않는 유령** 이었다. 줄을 지웠다.

**그런데 왜 살아남았는가 — 가드가 지키고 있었다.** `verify-snaps-env.mjs` 의
필수 목록에 `'# SNAPS_INBOX_CLEAR_CONFIRM='` 이 들어 있어서, 지우려 하면 검증이
실패한다. 한쪽 가드는 **존재를 요구** 하고, 어느 가드도 **읽히는지는 묻지 않았다.**
가드가 결함을 붙잡아 둔 셈이다.

고침 둘:
- `verify-snaps-env.mjs` 의 요구에서 제거.
- 기존 "모든 확인 스위치가 .env.example 에 있다" 가드에 **반대 방향** 추가: 문서에
  있는 `*_CONFIRM` 은 스크립트가 읽어야 한다. 그리고 그 가드가 스크립트 **4개를
  이름으로 나열** 하고 있어서(새 스모크는 목록에 안 들어간다) `scripts/` 전체 스캔으로
  바꿨다.

변이 3/3 예상대로. 그리고 **대조군 하나가 틀린 것은 제 쪽이었다** — `# ` 를 떼고
`SNAPS_PIXELLE_CONFIRM="generate"` 로 만드는 것을 "의미 보존"이라 봤는데, 가드가
주석 표시를 요구하는 데는 이유가 있다: 주석이 풀린 확인 스위치는 이 파일을 복사한
사람에게 **라이브 렌더가 미리 승인된 상태** 를 준다. 가드가 옳고 제 대조군이 틀렸다.

## 172. 틱톡 캡션 상한이 플랫폼보다 200자 관대했다

171번의 모양("존재는 요구하고 쓰임은 안 묻는다")을 한 겹 위로 올려 물었다.

정직한 음성 셋:
- **검증 스크립트 20개 전부** npm 에서 호출된다. 아무도 안 돌리는 검사기는 없다.
  (돈이 드는 deepseek 2개가 preflight 밖인 것은 의도.)
- `expectContains` 바늘 920개 중 66개가 약하다(대상에서 5회 이상 등장하거나 8자
  미만). 다만 이들은 "어딘가에 있다"를 주장할 뿐 무효는 아니다 — 최상위
  `readSnapsError(response)` 30회를 실제로 세어 보니 **`response.ok` 검사 31곳에
  `readSnapsError` 31개**, 카드뉴스·쇼츠도 일치. 오류 처리는 균일하다.
- 그래서 제품 쪽으로 갔다.

**snaps 의 플랫폼별 상한 vs 프로바이더가 실제로 강제하는 값** 을 맞춰 봤다.
프로바이더는 `maxLength() { return N; }` 로 진실을 들고 있다.

| 플랫폼 | snaps | 프로바이더 | |
|---|---|---|---|
| instagram | 2200 | 2200 | 일치 |
| linkedin | 3000 | 3000 | 일치 |
| naver-cafe | 10000 | 10000 | 일치 |
| youtube | 5000 | 5000 | 일치 |
| **threads** | 1500 | 500 | **오탐 — 아래** |
| **tiktok** | 2200 | 2000 | **결함** |

**Threads 는 결함이 아니었다.** `postMaxLength: 500` 이 따로 있고 1,500 은 답글
체인 전체이며, `publishing-payload.builder.ts` 가 500자 세그먼트로 쪼갠다. 제
탐지기가 **엉뚱한 필드를 비교** 했고, 블록을 읽어서 알았다. 숫자만 보고 고쳤다면
멀쩡한 설계를 망가뜨릴 뻔했다.

**TikTok 은 진짜다.** `postMaxLength` 가 없으니 2,200자가 한 캡션으로 나간다.
2,000~2,200 사이 캡션은 작성 시 "들어간다"는 말을 듣고 예약되고 **발행에서
거부된다** — 운영자는 에디터가 아니라 실패한 게시물로 알게 된다. 2000 으로 고쳤다.

가드는 숫자를 또 적어 두는 대신 **플랫폼마다 프로바이더와 비교** 한다 —
`postMaxLength ?? maxLength` 가 프로바이더의 `maxLength()` 를 넘으면 실패. 움직이는
쪽은 플랫폼이므로 이쪽이 오래간다. 비교된 플랫폼이 4개 미만이면 "이름이 안 맞는
것"으로 보고 **스스로 실패** 한다.

변이 4/4 예상대로 — tiktok 되돌리기, threads 의 `postMaxLength` 제거(체인 전체를
한 게시물로 약속하게 됨), instagram 을 1자 넘기기, 그리고 대조군(더 엄격한 값) 통과.

## 173. 제가 세 회차 동안 고친 그 결함을, 제 새 가드가 그대로 저질렀다

172번의 방법(선언을 강제자와 맞춰 보기)을 나머지 규칙 필드로 넓혔다.

정직한 음성 둘:
- 프로바이더는 미디어 상한을 선언하지 않는다 — 맞춰 볼 진실이 없다.
- `requiresTitle: true` 인 네 채널 중 **자동 발행은 둘**(youtube, naver-cafe)이고

**그런데 이 음성을 잠그려고 쓴 가드가 틀렸다.** 첫 실행에서 *threads 가 제목을

고침: 중괄호로 짝을 맞추는 `objectEntry()` 를 넣고 두 순회 모두 교체. 172번 변이

값의 출처와 값의 바닥은 다른 것이다. 기본 문자열 리터럴(`? x : 'snaps ...'`)을
요구하도록 좁히니 3/3.

교훈: **경계를 자르는 헬퍼는 그 경계가 존재하는 문맥에서만 쓴다.** 폴백이 있는
헬퍼는 폴백으로 떨어지는 순간 조용히 창으로 되돌아간다.

## 174. 165번의 "묶었다"는 절반이 사실이 아니었다

173번의 교훈은 "폴백이 있는 헬퍼는 경계가 없으면 조용히 창으로 되돌아간다"였다.
그러면 **지금 몇 개가 되돌아가 있는가** 를 세는 것이 다음 질문이다.

`methodBody`/`routeBody`/`declarationBody` 호출을 전부 실행해 봤다 — 대상과 앵커를
풀고, 헬퍼 자신의 경계 정규식을 적용하고, 안 맞으면 폴백이다.

```
16 calls resolved, 1 unresolved, 4 fell back to a window
   declarationBody  snaps-shorts-workspace.tsx  const loadHealth
   declarationBody  snaps-workspace.tsx         const loadList = async
   declarationBody  snaps-workspace.tsx         const engineLabel
   declarationBody  snaps-workspace.tsx         const applyPreparedAgentResult
```

넷 다 **컴포넌트 본문 안의 들여쓴 const** 다. `declarationBody` 의 경계는 열 0의
`const` 를 찾으므로 여기서는 **존재할 수 없고**, 전부 고정 2,000자 창으로 떨어져
있었다. **즉 165번에서 "선언 앵커 6개를 묶었다"고 보고한 것 중 4개는 묶이지
않았다.** 제 보고를 정정한다.

고침: `declarationBody` 가 경계 대신 **괄호 짝** 으로 선언의 끝을 찾는다.

처음 구현은 틀렸다 — 첫 번째 여는 괄호를 잡았더니 `const loadHealth = async () => {`
의 **빈 매개변수 목록** 이 즉시 닫혀 시그니처만 돌려줬다(그래서 가드가 "loadHealth
가 실패 이유를 기록하지 않는다"고 잘못 실패했다). 세 종류 괄호를 **하나의 깊이** 로
세고, 깊이가 0으로 돌아왔을 때 **뒤에 `;` 가 올 때만** 끝으로 본다. 재측정: **폴백
0개.**

**결정적 증명:** `setHealthError` 를 loadHealth 에서 빼고 **바로 아래 선언에** 넣는
변이를 만들었다. 지금은 잡힌다. 그리고 헬퍼를 옛 형태로 되돌려 같은 변이를 돌리니
**통과했다** — 옛 헬퍼가 이웃을 읽고 있었다는 것이 측정으로 확인됐다.

교훈: **"묶었다"는 보고는 경계가 실제로 맞았는지 세어 본 뒤에만 할 수 있다.**
헬퍼를 호출했다는 사실은 묶였다는 뜻이 아니다.

## 175. 다음번에 조용히 창으로 되돌아가면 이번엔 소리가 난다

173·174번은 같은 사고를 두 번 다르게 겪었다 — 경계 헬퍼가 경계를 못 찾으면 고정
창으로 떨어지는데 **아무도 그 사실을 모른다.** 174번에서 4건을 손으로 세어 고쳤지만,
그건 이번 4건을 고친 것일 뿐 **부류를 없앤 것이 아니다.**

그래서 검증기가 **스스로를 검사** 하게 했다. 세 헬퍼가 폴백을 쓸 때마다 기록하고,
모든 가드가 돈 **뒤** 마지막에 그 목록이 비었는지 본다.

던지지 않고 기록하는 이유: 클래스의 **마지막 멤버** 에는 다음 경계가 없으므로
폴백이 정당하다. 정당한 경우와 사고를 구분하는 것은 개별 헬퍼가 아니라 전체를 본
뒤의 판단이다.

**증명이 이번 회차의 핵심이다.** 변이 3/3:
1. `declarationBody` 가 종결자를 못 찾게 망가뜨림 → **잡힘**(exit 1).
2. 같은 고장 + **기록기를 제거** → **통과**(exit 0). 즉 **이전 상태에서 일어나던
   일을 그대로 재현** 했다. 자기검사가 없으면 망가진 헬퍼는 조용하다.
3. 대조군(기록 문자열 개명) 통과.

2번이 핵심이다 — 가드가 잡는 것이 아니라 **기록기가 잡는다** 는 것을 보여 준다.

교훈: **한 번 겪은 사고는 고치고, 두 번 겪은 사고는 스스로 신고하게 만든다.**

## 176. 카드뉴스 슬라이드에 `Dr.` 한 장이 만들어지고 있었다

제품으로 돌아왔다. 한국어 텍스트 파이프라인은 이 제품의 핵심이고, 문장 분할기의
결과는 **그대로 카드뉴스 슬라이드와 쇼츠 장면이 된다.**

이 파일은 이미 여러 번 손봤고 주석이 일곱 가지 입력 모양을 측정해 적어 두었다.
그래서 **주석이 다루지 않은 모양** 으로 쟀다 — 운영자가 실제로 붙여 넣는 것들.

15개 중 3개가 조각을 만들었고, 그중 **하나는 제 탐지기의 오탐** 이었다
(`대박!정말 좋아요.` → `['대박!', '정말 좋아요.']` 는 **옳은** 분할인데, 3자 이하에
문장부호로 끝난다는 이유로 걸렸다). 진짜는 둘:

```
Dr. Kim이 추천한 방법입니다.  ->  ['Dr.', 'Kim이 추천한 방법입니다.']
vs. 경쟁 제품과 비교했습니다.  ->  ['vs.', '경쟁 제품과 비교했습니다.']
오전 9시 a.m. 시작합니다.     ->  세 조각
```

**이미 고쳐진 숫자 규칙의 거울상이다.** `1.` 과 `2026. 9. 12.` 는 살아남는데
라틴 약어는 뜯긴다. 이유도 같다 — **한국어 문장은 한글 음절로 끝나지 라틴 낱말로
끝나지 않으므로, 마침표 앞의 글자는 약어다.**

고침: 두 lookbehind 의 `[0-9]` 를 `[0-9A-Za-z]` 로. 숫자 규칙이 이미 치르는 것과
**같은 대가** 를 치른다 — 한국어 안에 낀 영어 문장(`This is great. 다음 주에...`)이
한 덩어리로 남는다. 숨기지 않고 **테스트에 그대로 적어 두었다**(줄바꿈이 있으면
여전히 나뉜다는 것도 함께).

변이 4/4 예상대로 — 라틴 절반 제거, 숫자 절반 제거, 줄바꿈 규칙 약화, 그리고
대조군(문자 클래스 순서 바꾸기) 통과.

교훈: **이미 여러 번 고쳐진 파일이라도, 주석이 측정한 목록 밖에서 재면 아직 남아
있다.** 그리고 **제 탐지기가 낸 경고 셋 중 하나는 틀렸다** — 자동 판정은 읽어 보고
받아들여야 한다.

## 177. X 글자 수 계산이 링크 하나 때문에 양쪽으로 틀렸다

176번의 방법(잘 다듬어진 파일을 그 주석이 다루지 않은 입력으로 재기)을 형제 파일에
적용했다. `weighted-length.ts` 는 X 의 가중치 규칙을 신중하게 구현했고 주석도
정직하다 — 그런데 **링크를 한 번도 고려하지 않았다.**

X 는 모든 URL 을 t.co 로 바꾸고 **길이와 무관하게 23 단위** 로 센다
(twitter-text 의 `transformedURLLength`). 마케팅 캡션에 링크가 없는 경우가 오히려
드물다. 한국어 한 문장 + 링크로 쟀다:

| 입력 | snaps 계산 | X 실제 | 결과 |
|---|---|---|---|
| `https://s.io/a` | 62 | **71** | **9 단위 과소 계산 — 발행에서 거부될 수 있다** |
| UTM 붙은 링크 | 155 | **71** | **84 단위 낭비 — 한글 약 42자를 이유 없이 잘라낸다** |

**두 방향 다 실재한다.** 짧은 링크는 과소 계산이라 "들어간다"고 말한 글이 X 에서
거부되고 — 이 파일이 존재하는 이유가 바로 그것이다 — 긴 링크는 과대 계산이라
운영자의 문장을 공짜로 깎는다.

고침: 텍스트를 **가중치를 지는 토큰 목록**(링크 하나 = 23, 나머지는 문자별)으로
만들고, 길이 계산과 클램프가 같은 목록을 쓴다. **링크는 자르지 않는다** — 반쪽
링크는 짧은 링크가 아니라 깨진 링크이고, 23 단위도 아니다.

명시적 `http(s)` 만 이렇게 센다. 맨 `example.com` 도 X 는 링크로 만들지만, 그건
문장 중간의 브랜드 이름을 쓰는 방식이기도 하다 — **산문을 과대 계산하는 쪽이 더 나쁜
실수** 라서 보수적으로 뒀다.

**제 테스트 하나가 틀렸다.** "링크가 살아남는다"를 단언했는데 산문만으로 이미 예산을
넘는 입력이었다. 클램프는 꼬리를 자르고 링크는 꼬리에 있다 — **코드가 아니라 제
기대가 틀렸다.** 고치면서 그 동작을 **숨기지 않고 테스트에 적어 두었다**: 산문이
이미 넘치면 링크도 함께 잘린다.

변이 4/4 예상대로 — 문자수로 되돌리기, 23 을 20 으로 흘리기, 링크 중간에서 자르기,
그리고 대조군(토큰 함수 개명) 통과.

## 178. 문서가 약속한 것을 폴백이 지키지 않았다 (도달 불가였지만)

핵심 텍스트 헬퍼 셋째. `clamp-text.ts` 는 자르는 위치를 자소 경계로 되돌리는
신중한 구현이고, 맨 위 주석이 이렇게 약속한다 — *"피부색 수정자나 ZWJ 가족
시퀀스가 **다른 사람으로 보이는 조각들** 로 찢기지 않게 한다."*

**한 위치만 고르지 않고 모든 위치에서 잘라 봤다.** 한국어 캡션이 실제로 담는
자소 모양들(국기=코드포인트 2개, ZWJ 가족, 피부색, 키캡=숫자+VS16+감싸는 표시,
결합 악센트, **분해형 한글**)로 86개 절단 위치를 검사:

```
4 broke a cluster
  keycap            limit=1 -> "1"      (키캡이 사라진 숫자)
  keycap            limit=2 -> "1️"      (매달린 변이 선택자)
  decomposed hangul limit=1 -> "ᄒ"      (홀로 남은 초성)
  decomposed hangul limit=2 -> "하"      (다른 글자)
```

전부 **첫 자소가 예산보다 큰** 경우다. 코드는 거기서 의도적으로 코드포인트 절단으로
빠진다 — 주석 왈 *"아무것도 안 남기는 것이 더 많이 잃는다."*

그런데 그 폴백이 내놓는 것이 **맨 위 주석의 약속과 모순된다.** 특히 `한` → `하` 는
**짧아진 글자가 아니라 다른 글자** 다. 그리고 분해형은 가상의 입력이 아니다 —
해시태그 헬퍼 주석이 이미 *"macOS 를 거친 텍스트는 분해형으로 도착한다"* 고 적어
두었다.

**도달 가능성부터 쟀다:** 호출자가 쓰는 가장 작은 예산은 **80** 이다. 그러니
오늘 실행되는 코드에는 영향이 없다. 그럼에도 고친 이유는, 이것이 **잠재적으로
조용히 틀린 출력** 이고 한 줄이면 약속이 참이 되기 때문이다.

고침: 인덱스 0 도 자소 경계다. `end > 0` 조건을 없애 자소 경로가 언제나 결정하게
했다. **오늘 도는 것은 아무것도 바뀌지 않는다**(최소 예산 80) — 약속이 *거의*
참에서 참이 될 뿐이다. 재측정 86/86 통과.

변이 4/4 예상대로 — 0 경계 건너뛰기 복원, 자소 경로 자체 제거, 경계가 예산을 1
넘도록 허용, 그리고 대조군(경계 커서 개명) 통과.

교훈: **주석이 약속한 불변식은 폴백 경로에서도 지켜져야 한다.** 폴백은 "덜 좋은
답"이지 "약속을 깨도 되는 곳"이 아니다.

## 179. 보이지 않는 글자가 발행된 글에 실려 나가고 있었다

핵심 텍스트 헬퍼 넷째. `body-text.ts` 는 줄바꿈을 지키려고 만들어진 파일이고
주석이 측정 결과까지 적어 두었다. 그래서 **주석이 다루지 않은 것** 을 쟀다 —
운영자가 웹페이지나 워드에서 붙여 넣을 때 딸려 오는 **보이지 않는 글자들.**

8가지 중 **6가지는 이미 처리** 된다(비분리 공백, BOM, U+2028, U+2029 — 전부
자바스크립트 `\s` 에 포함되니까). 정직한 음성이다. 남은 둘:

- **U+200B 영폭 공백** — 많은 웹 에디터가 줄바꿈 힌트로 넣는다.
- **U+00AD 소프트 하이픈** — 워드가 남긴다.

둘 다 발행되는 글에 그대로 실린다. 보이지 않는 채로 **길이 예산을 먹고**, 플랫폼
검색에서 **단어를 쪼갠다.**

**그리고 U+200D 결합자는 살아남는다 — 살아남아야 한다.** 이모지 가족을 묶고 있는
것이 그것이라, 지우면 그림 하나가 사람 셋이 된다. 그래서 U+200C/U+200D 는 건드리지
않고 U+200B·U+00AD·U+2060 만 지운다.

변이 3/4 예상대로. 살아남은 하나는 **테스트 구멍이 아니라 제 변이가 무의미했던
것** 이다 — `[^\S\n]+` 를 `\s+` 로 바꾸는 변이였는데, 그 코드는 `split('\n')`
**뒤에** 각 줄에 적용되므로 줄 안에는 개행이 없다. 두 정규식은 거기서 **동치** 다.
(원래 결함은 분할 *전* 전체 텍스트에 적용될 때의 것이었고, `[^\S\n]` 표기는 그
분할이 사라질 경우를 대비한 방어적 문서다.)

교훈 반복: **변이가 살아남으면 테스트를 의심하기 전에 변이가 무언가를 바꾸긴
했는지 확인한다.**

## 180. `가-힣` 을 읽는 곳마다 분해형 한글에 눈이 멀어 있었다

텍스트 헬퍼 다섯째, `media-file-name.ts`. 필터가 `[^\w.\-가-힣]` 다. 그런데
`가-힣` 은 **조합형 음절 블록** 이고, macOS 파일시스템을 거친 텍스트는 **분해형** 으로
도착한다 — 이 사실은 `sanitizeSnapsHashtags` 주석이 **이미 적어 두었다.**

측정: 분해형 `환절기영상.mp4` → **`______________.mp4`**.

그래서 `가-힣` 을 읽는 **다른 곳을 전부** 찾았다. 7곳이고, 셋은 피해가 명확했다:

| 위치 | 조합형 | 분해형 |
|---|---|---|
| `media-file-name` 파일명 | `환절기영상.mp4` | `______________.mp4` |
| `normalizeMetricKey` 지표 키 | `좋아요` / `댓글` | **둘 다 `metric`** |
| 쇼츠 음절 수 | 17 | **1** |

가운데 것이 가장 나쁘다 — **서로 다른 두 지표가 같은 키가 되어 리포트가 둘을
합산** 한다. 168번의 중복 합산과 같은 결과인데 원인이 유니코드 정규화다. 셋째는
쇼츠 타임라인이 음절 수에 비례해 장면 시간을 나누므로, 분해형이면 **모든 장면이
똑같이 나뉘고** 그 수에 의존하는 "읽기에 너무 길다" 경고가 **영영 뜨지 않는다.**

고침: 패턴마다 자모 범위를 덧붙이는 대신 **한 철자로 모아서 읽는다**
(`snapsComposeHangul`, NFC). 두 형태는 같은 낱말이고, 하류의 중복 제거·키·세기가
모두 한 철자를 전제로 쓰여 있다. 해시태그 정리기가 이미 같은 선택을 했다.

변이 4/4 예상대로 — 세 곳 각각의 NFC 제거가 모두 잡히고, 대조군(이미 조합형인
텍스트를 한 번 더 조합) 통과.

**남은 네 곳은 정직하게 적어 둔다** — `vector-store` 의 `HANGUL_START`,
`command-planner` 의 주제 추출, `split-sentences` 의 lookahead, `report-generator`
의 키 정규화. 같은 맹점이지만 **측정된 피해를 아직 못 찾았다.** 다음에 그쪽 입력을
재 볼 것.

## 181. 남겨 둔 네 곳을 재 보니 넷 다 깨져 있었다

180번은 `가-힣` 을 읽는 일곱 곳 중 셋을 고치고 **넷은 "피해를 아직 못 찾았다"고
적어 두었다.** 그 넷을 분해형 입력으로 쟀다 — **넷 다 깨진다.**

| 위치 | 조합형 | 분해형 |
|---|---|---|
| `report-generator.normalizeKey` | `좋아요` / `댓글` | **둘 다 `""`** |
| `vector-store.HANGUL_START` | true | false |
| `command-planner.detectTopic` | `환절기 건강 관련` | **null** |
| `split-sentences` lookahead | 2문장 | **1문장** |

첫 줄이 가장 나쁘다 — 이건 **리포트가 실제로 지표를 묶는 키** 이고, 분해형이면
서로 다른 지표 둘이 **빈 문자열 하나** 로 합쳐진다. 180번에서 고친 매퍼의 키는 그
앞단이고 이쪽이 본진이었다. 셋째는 운영자가 쓴 주제를 **말없이 잃는다.** 넷째는
분해형 붙여넣기가 **슬라이드 한 장** 이 된다.

넷 다 각자의 읽는 지점에서 NFC 로 모으게 했다. 문장 분할기는 가장 넓게 닿는
곳이라 함수 입구에서 모은다.

**그리고 이 부류가 스스로 신고하게 만들었다.** 새 가드: `가-힣` 을 **코드에서**
(주석 말고) 읽는 snaps 파일은 `snapsComposeHangul` 을 써야 한다. 읽는 파일이 5개
미만이면 "패턴이 깨졌다"며 스스로 실패한다.

변이 3/3 예상대로 — 기존 reader 가 모으기를 그만두기, **새 reader 가 모으지 않고
등장하기**, 그리고 대조군(주석에만 블록을 언급) 통과.

교훈: **"피해를 못 찾았다"는 "피해가 없다"가 아니다.** 180번에 그렇게 적어 두고
다음 회차에 재 봤더니 넷 다 있었다. 적어 두지 않았으면 넘어갔을 것이다.

## 182. 제가 어제 만든 가드에 구멍이 있었다 — 블록의 다른 철자

181번에서 "`가-힣` 을 읽는 파일은 모아서 읽어야 한다"는 가드를 만들었다. 오늘
카드뉴스 렌더러를 보다가 **그 가드가 이 파일을 통째로 건너뛴다** 는 것을 알았다.

이유: 렌더러는 블록을 `가-힣` 이 아니라 **코드 포인트로** 쓴다.

```ts
(code >= 0xac00 && code <= 0xd7a3) || // Hangul syllables
(code >= 0x1100 && code <= 0x11ff) || // Hangul Jamo
```

`grep -c 가-힣` → **0**. 제 가드는 지키려던 것의 **한 가지 철자만 알고 있었다.**

그리고 실제로 깨져 있었다. 이 폭 표는 **자모 하나를 음절 하나만큼** 청구하므로,
분해형 음절은 **세 번** 청구된다. 측정(`환절기 건강 관리`, 62px):

```
composed   436.5
decomposed 1121.0   = 2.57x
```

제목이 여백에 닿기 한참 전에 줄바꿈되고 말줄임표가 붙으며, 덱은 그것을
**trimmed 로 보고** 한다 — 운영자는 자르지 않아도 될 문구를 잘랐다고 듣는다.

고침 둘:
- 렌더러가 `toText()` 와 `measureText()` 양쪽에서 모은다. `toText` 는 그려지는
  SVG 까지 조합형으로 만들고(번들 폰트가 글리프를 가진 형태), `measureText` 는
  **블록을 읽는 자리** 라 호출자에 기대지 않고 스스로 보장한다.
- 가드가 블록의 **다른 철자들**(`0xac00`, `0xd7a3`, `0x1100`, `\u{ac00}`)도
  알아본다.

변이: 렌더러 2/2, 가드 3/3, 그리고 **결정적인 것 1/1** — 코드 포인트로만 블록을
부르는 파일에서 모으기를 없애니 이제 가드가 잡는다(어제는 못 잡았다).

교훈: **가드는 자기가 지키는 것의 철자를 전부 알아야 한다.** 하나만 아는 가드는
"검사했다"고 말하면서 검사하지 않는다 — 제가 남의 코드에서 계속 찾아내던 바로 그
모양이고, 이번엔 만든 지 하루 된 제 가드였다.

## 183. 이번 창에서 제가 쓴 가드 넷이 한 가지 철자만 알고 있었다

182번이 "가드는 자기가 지키는 것의 철자를 전부 알아야 한다"였으니, **이번 창에서
제가 추가한 가드들** 을 같은 잣대로 쟀다. 방법은 간단하다 — **의미를 바꾸지 않는
재작성** 을 대상 파일에 적용하고 가드가 통과하는지 본다.

첫 표적(170번의 버튼 가드)부터 **둘 다 깨졌다**:

```
disabled={loading || props.disabled}                  -> BROKE
disabled={Boolean(props.disabled) || Boolean(loading)} -> BROKE
```

둘 다 같은 뜻이고 같은 동작인데, 가드는 `disabled={props.disabled || loading}`
**한 철자, 한 순서** 만 인정했다. 성질은 "**disabled 가 loading 에 의존한다**"이지
그 표현식의 철자가 아니다.

같은 잣대로 이번 창의 나머지도 보니 셋 더 나왔다 — 전부 **이름에 묶여** 있었다:

| 가드 | 묶여 있던 것 |
|---|---|
| 버튼 비활성화 | 피연산자 순서 |
| Ollama 재시도 | `snapsWasTimeout(error)` 의 **매개변수 이름** |
| 전환 신호 상한 | `count = Math.min(` 의 **지역변수 이름** |
| 인용문 검사 | `quoteFromItems(example, items)` 의 **인자 이름 둘** |

넷 다 모양 기반으로 바꿨다. **그리고 느슨하게 만든 뒤 다시 무는지 확인했다** —
느슨해진 가드는 통과만 하고 아무것도 안 지킬 수 있다. 6/6:
버튼 비활성화 제거·`loading` 무시, Ollama 타임아웃 검사 제거, 상한 제거, 인용문
검사 제거가 **전부 잡히고**, 대조군(catch 매개변수 **진짜** 개명)이 통과.

마지막 줄에 주의할 점이 있다. 166번에서 같은 대조군을 돌렸을 때는 통과했는데,
그건 제 변이가 `const error = failure;` 라는 **별칭을 남겨 두었기 때문** 이다.
진짜 개명은 지금까지 깨졌을 것이다. **대조군도 진짜여야 한다.**

교훈: **파괴 변이보다 "의미를 바꾸지 않는 재작성"을 먼저 써라.** 전자는 테스트가
무는지 보고, 후자는 가드가 **너무 많이 무는지** 본다 — 그리고 이번 창에서 실제로
잘못돼 있던 쪽은 후자였다.

## 184. 순서에 묶인 가드를 기계로 찾았다 — 여덟 중 다섯

183번은 제 가드 넷을 손으로 찾아 고쳤다. 손으로 찾는 것은 부류를 없애지 못하므로
**기계로** 찾았다: 교환 가능한 불리언(`&&`, `||`)을 담은 바늘은 순서에 묶여 있다.
피연산자를 바꾸는 것은 의미를 바꾸지 않으니, 그 재작성에 깨지는 가드는 성질이 아니라
철자를 지키고 있는 것이다.

**8개** 가 나왔고, 읽어 보니 **3개는 정당한 제외** 였다:

- `body && typeof body === 'object' && ...` — 앞의 `body &&` 가 null 검사다.
- `저장 원문 "${a || b}"...` — 사용자에게 보이는 **메시지 문자열** 이고, `||` 는
  대체값 순서라 바꾸면 동작이 달라진다.
- `{selectedPlatforms.includes('naver-cafe') && <...>}` — JSX 조건부 렌더. 오른쪽
  피연산자가 그려질 요소라 교환 불가능.

**나머지 다섯은 진짜** 였다:

| 가드 | 바늘 |
|---|---|
| 빈 변형 거부 | `!hasBody && !hasMedia` |
| 공용 타임아웃 파서 | `Number.isFinite(parsed) && parsed > 0` |
| 오케스트레이터 타임아웃 파서 | 같은 식(사본) |
| RAG 재생성 토스트 | `rebuiltTotal && !rebuiltCount` |
| 링크 스팸 판정 | `link && promo` |

`testsBothWays(source, left, right)` 하나를 만들어 다섯을 모두 양쪽 순서로 읽게
했다.

**양방향으로 검증했다 — 9/9.** 파괴 쪽 넷(빈 변형 검사 제거, 유한성 검사 제거,
재생성 조건 약화, 링크 단독 스팸화)이 **전부 잡히고**, 대조군 다섯(각 식의 피연산자
교환)이 **전부 통과** 한다. 느슨하게 만든 가드가 여전히 무는지 확인하지 않으면
"고쳤다"가 "없앴다"가 된다.

(도중에 재생성 변이의 대상 파일을 벡터 스토어로 잘못 적었다. `rebuiltTotal` 은
**프런트 워크스페이스** 의 지역변수다. 앵커가 0번 일치해 도구가 잡아 줬다.)

교훈: **"손으로 넷 고쳤다"와 "그 부류를 없앴다"는 다르다.** 기계로 세어야 남은
수를 말할 수 있다.

## 185. 세 개를 찾은 줄 알았는데 제 탐지기가 엉뚱한 파일을 보고 있었다

172번의 방법(선언을 강제자와 맞춰 보기)을 새 표적에 적용했다: **프로바이더의 설정
DTO 가 요구하는 필드를 snaps 가 채우고 있는가.** snaps 는 발행 페이로드를 직접
만들므로, 빠진 필드를 채워 줄 곳이 없고 **플랫폼이 거부할 때까지 아무도 모른다.**

첫 실행은 셋을 신고했다 — instagram 의 `post_type`, tiktok 의 여덟 개, x 의
`who_can_reply_post`.

**셋 다 오탐이었다.** 제 탐지기가 `publishing-payload.builder.ts` 만 뒤졌는데,
플랫폼별 설정은 대부분 `platform-rules.ts` 의 `buildDefaultSettings()` 에서
심어진다. 그 파일을 범위에 넣으니 **전부 공급됨**.

그리고 tiktok 쪽은 한 겹 더 확인했다 — 프로바이더가
`settings.privacy_level || 'PUBLIC_TO_EVERYONE'` 처럼 **전부 기본값을 갖는다.**
DTO 가 required 라고 표시한 것과 발행 시 실제로 필요한 것은 다르다.

**음성을 믿기 전에 탐지기를 증명했다:** `post_type: 'post',` 를 지우고 다시 돌리니
`instagram  InstagramDto  post_type` 이 뜬다. 탐지기는 작동하고, 오늘은 정말로
빠진 것이 없다.

그래서 이 음성을 **가드로 잠갔다.** 자동 발행하는 채널마다 프로바이더의 `dto = X`
를 찾아 required 속성을 읽고, snaps 가 그것을 심는지 본다. DTO 에 맞춰진 채널이
3개 미만이면 "이름이 안 맞는다"며 스스로 실패한다. 프로바이더가 필수 설정을
추가하거나 새 채널이 자동 발행을 시작하면 **발행이 아니라 여기서** 걸린다.

변이 3/3 예상대로 — `post_type` 제거, tiktok 필드 하나 개명, 그리고 대조군(심어진
설정의 순서 바꾸기) 통과.

교훈 반복: **탐지기가 신고한 것을 고치기 전에 탐지기가 맞는 곳을 보고 있는지
확인한다.** 172번에서는 엉뚱한 *필드* 를 봤고(threads), 이번엔 엉뚱한 *파일* 을
봤다. 둘 다 고쳤다면 멀쩡한 코드를 망가뜨렸을 것이다.

## 186. `1시간 뒤에 올려줘` 가 다음 날 새벽 1시로 예약됐다

한국어 시간 표현 파서를 쟀다. 이 함수의 결과는 **그대로 예약 시각** 이 되므로
틀리면 아무도 고르지 않은 순간에 글이 나간다. 주석에 측정 기록이 여럿 있어서
**주석이 다루지 않은 표현** 으로 시험했다(2026-05-12 화요일 14:00 KST 기준).

문서화된 여섯 가지는 전부 정확했다. 그리고 둘이 틀렸다:

```
내일 3시 반에 올려줘   -> 03:00      (반이 사라짐)
1시간 뒤에 올려줘      -> 다음 날 01:00
```

**두 번째가 심각하다.** 시간 정규식이 `시간` 의 `시` 를 **시각으로** 읽었다.
오후 2시에 "한 시간 뒤"라고 말하면 15:00 이 되어야 하는데, **날짜까지 틀린**
다음 날 새벽 1시가 나온다. `2시간 동안`, `3시간 후` 같은 표현도 전부 같은 함정에
걸린다 — 그리고 조용하다.

고침 둘:
- `시(?!간)` — `시간` 은 기간이지 시각이 아니다. 상대 오프셋 파싱은 이 함수에
  없으므로, **시각을 아예 읽지 않는 것이 정직한 결과** 다. 기본값이 그대로 선다.
- `반` 을 30분으로 읽는다.

변이 4/4 예상대로 — `시간` 예외 제거, `반` 읽기 제거, `반` 을 60분으로 만들기,
그리고 대조군(반 그룹을 지역변수로 빼기) 통과.

**남겨 두는 것 둘, 정직하게:**
- **상대 오프셋**(`1시간 뒤`, `30분 후`)은 여전히 파싱하지 않는다. 이제 잘못된
  시각을 지어내는 대신 읽지 않을 뿐이다. 구현은 기능 추가라 별도 판단이 필요하다.
- **마커 없는 `3시`** 는 문자 그대로 03:00 이다. 한국어에서 마커 없는 `3시` 는
  중의적이고, 오후로 추정하는 것은 **운영자가 말하지 않은 것을 지어내는 일** 이라
  건드리지 않았다.

## 187. "올리지 마"라고 쓴 다섯 문장 중 넷이 발행됐다

발행 여부를 정하는 두 판정자(`looksLikePublishIntent`, `refusesToPublish`)를 쟀다.
이 둘의 곱이 **글이 나가느냐 마느냐** 를 정한다.

단순한 명령 17개 중 16개가 옳았다. **그런데 세 개가 운으로 옳았다** — `업로드는
하지 마`, `올리면 안 돼`, `포스팅 금지` 는 거절 규칙이 아니라 **발행 의도가 없어서**
초안이 됐다. 즉 같은 문장에 발행 단어가 함께 있으면 무너진다.

그 모양으로 다시 쟀다. 운영자는 보통 **할 일을 설명하고 나서 한계를 말하므로**
이것이 실제 명령의 모양이다:

```
내일 올려야 하는데 오늘은 포스팅 금지야      -> PUBLISH
예약 글 준비해줘. 업로드는 하지 마.         -> PUBLISH
게시할 내용 정리해줘. 게시는 하지 말고.      -> PUBLISH
발행용 원고 써줘. 발행은 보류.             -> PUBLISH
```

**다섯 중 넷이 운영자가 방금 보내지 말라고 한 것을 보낸다.**

원인은 거절 어휘가 좁았다는 것이다. 기존 패턴은 어간과 `지 마` 가 **붙은** 형태
(`업로드하지 마`)만 읽는데, 명사에 조사가 붙어 갈라진 형태(`업로드는 하지 마`)가
한국어에서 더 흔하다. `금지`·`보류` 는 아예 없었다.

추가한 것 셋: **명사+조사+하지 마/말**, **금지|보류|중단**, **~면 안 돼**.

**변이 하나가 살아남아 제 테스트가 약함을 드러냈다** — 원래의 `초안으로만` 규칙을
통째로 지워도 통과했다. 그 사례(`초안으로만 만들어줘`)에는 **발행 단어가 없어서**
규칙이 없어도 초안이 되기 때문이다. `내일 인스타에 올려줘. 아니다, 초안으로만.`
을 넣으니 그 규칙이 비로소 일을 한다. **5/5 예상대로.**

교훈: **"맞았다"가 "그 규칙 덕분에 맞았다"는 뜻은 아니다.** 판정이 옳게 나온 사례
중 셋은 다른 이유로 옳았고, 그 셋이 진짜 결함이 숨어 있던 자리였다.

## 188. `카드뉴스 금지` 라고 쓰면 카드뉴스가 만들어졌다

187번에서 발행 거절 어휘가 좁다는 것을 고쳤으니, **형제** 를 봤다 — 형식(카드뉴스·
쇼츠)을 정하는 `SNAPS_DENIAL_WORDS`. 같은 구멍이 있었다:

```
카드뉴스 금지   -> asksFor=true
카드뉴스는 보류  -> asksFor=true
쇼츠 금지야     -> asksFor=true
쇼츠는 중단     -> asksFor=true
```

**그리고 여기서는 더 나쁘다.** 162번에서 "요청은 거절만큼 명시적이다"를 구현했기
때문에 `asksFor=true` 는 이제 플래그를 **켠다.** 즉 `카드뉴스 금지` 라고 쓴 운영자가
**카드뉴스를 받는다.** 제 162번 수정이 좁은 어휘와 만나 생긴 결과다.

**그런데 단순히 단어를 추가하면 새 결함이 생긴다.** 이 세 단어는 평범한 **내용
단어** 이기도 하다. 14자 창에서 찾으면:

```
카드뉴스로 서비스 중단 안내 만들어줘   -> 거절로 읽힘 (틀림)
쇼츠로 주차 금지 안내 만들어줘        -> 거절로 읽힘 (틀림)
```

그래서 **형식에 붙은 경우만** 읽는다: `<형식>(은|는|이|가)? (금지|보류|중단)` 을
키워드 바로 뒤에 **앵커** 로 건다. 12개 사례 전부 통과 — 금지형 넷은 거절로,
내용어 셋은 요청으로.

변이 4/4 예상대로 — 금지 규칙 제거, **앵커 대신 창에서 찾기**(내용어가 거절이 된다),
세 단어 중 하나 빼기, 그리고 대조군(단어 순서) 통과. 두 번째 변이가 이 설계의
핵심을 지킨다.

교훈: **어휘를 넓힐 때는 그 단어가 내용으로도 쓰이는지 함께 재라.** 넓히기만 하면
한 방향 오류를 다른 방향 오류로 바꾸는 것으로 끝난다.

## 189. "정중하게 써줘" 가 반말 스타일로 계획됐다

188번의 수정이 `asksFor` 안에 들어갔으니 **한 겹 아래** 를 확인했다 — 채널 탐지도
같은 함수를 쓴다. 확인 결과 **그대로 전파됐다**(측정 5/5): `인스타 금지` 는 이제
채널로 읽히지 않고, `인스타로 서비스 중단 안내 올려줘` 는 여전히 인스타로 읽힌다.
한 자리를 고쳐 두 곳이 나아진 드문 경우라 **가정하지 않고 재서** 확인했다.

그러다 같은 파일의 `detectTone` 에서 다른 것이 보였다. 분기가 셋뿐이다 — 유머,
전문, 그리고 기본값인 **"한국 나노 인플루언서 스타일"**(반말 캐주얼). 한국어는
격식체를 명시적으로 표시하는데, 그 어휘가 하나도 없다:

```
정중하게 써줘     -> 캐주얼 기본값
격식 있게 써줘    -> 캐주얼 기본값
공손하게 부탁해    -> 캐주얼 기본값
존댓말로 써줘     -> 캐주얼 기본값
높임말로 작성해줘   -> 캐주얼 기본값
```

**운영자가 한 격식을 요청하면 정반대 격식이 계획된다.** 186번의 `반` 과 같은
부류다 — 말한 것이 조용히 버려진다.

고침: 격식 분기를 추가하되 **`asksFor` 를 통해** 읽는다. 그러면 `격식 없이 써줘`,
`정중한 건 빼고 편하게 써줘` 가 자동으로 캐주얼로 남는다 — 형식·채널 어휘가 이미
받고 있는 거절 처리를 그대로 물려받는다. 11개 사례 전부 통과.

변이 4/4 예상대로 — 격식 분기 제거, **`asksFor` 대신 직접 test**(거절이 무시된다),
어휘 하나 빼기, 그리고 대조군(어휘 순서) 통과. 두 번째가 이 설계의 핵심이다.

교훈: **기존 헬퍼를 통해 읽으면 그 헬퍼가 이미 배운 것을 공짜로 얻는다.** 새
`test()` 를 쓰면 거절 처리를 처음부터 다시 틀리게 된다.
